                    Octopus Control Protocol (OCP)

Abstract

   OCP is the session protocol of the OpenOcto ecosystem: a symmetric,
   binary and transport-independent general purpose robot control
   protocol in which a sixteen-octet header carries a message type, a
   flag octet, a sequence number and a payload length, and the payload
   is a single CBOR value.  Above the frame layer the protocol provides
   sessions, remote procedure calls, publish/subscribe and a byte-stream
   tunnel, together with one OPTIONAL top-layer transform: compression.
   Authentication is OPTIONAL: the initiator names one method of any
   kind and the responder either accepts it or fails. The protocol is
   general purpose: its core names no machine, no transport and no
   implementation, and what a peer offers is carried by profiles and by
   descriptors.  Cryptographic protection is deliberately not part of
   this document.  It is added by one of two extensions: the frame-layer
   primitives of [RFC0009], which also define a longer header, or a
   secure transport carrying the whole session [RFC0010].  The two are
   alternatives and are not used together.  The RECOMMENDED port for a
   TCP or a UDP binding is 6286; [RFC0010] recommends another for a
   secure transport.

1.  Introduction

   The protocol carries all control-plane traffic of the OpenOcto
   ecosystem: requests and responses, asynchronous notifications, and
   bulk byte streams.  It is designed so that a device-oriented
   implementation can be written from this document alone.

   The core semantic content of the protocol is:

   1.  sessions: establishment, capability and flag negotiation,
       OPTIONAL authentication, and graceful termination;

   2.  remote procedure calls, multiplexed by request identifier;

   3.  publish/subscribe: asynchronous notifications from a peer;

   4.  blob tunnels: named byte streams with flow control,
       retransmission and resumption;

   5.  structured values, encoded as CBOR.

   Heartbeats and metadata are not separate messages: both are ordinary
   procedure calls (Sections 9.1 and 6.3).

   OCP is a general-purpose control protocol for robots and for the
   devices attached to them.  It is deliberately silent about what is
   being controlled: the core defines sessions, three interaction
   patterns and one value encoding, and everything that depends on a
   particular machine is carried by profiles and by descriptors rather
   than by the protocol.

   *  Neutral about the machine.  The core names no motor, no joint and
      no bus.  It names five kinds of thing a device offers --
      procedures, sensors, actuators, parameters and events -- and
      leaves what each of them is to the peer, which reports them in
      metadata (Section 9.1).

   *  Neutral about the transport.  A binding has only to deliver
      delimited frames and to state whether it is reliable (Section 7),
      so one session runs unchanged over a stream, over a datagram
      service or over any other octet carrier.

   *  Neutral about the implementation.  The payload is a
      self-describing CBOR value (Section 4) and the state machine is
      small enough for a microcontroller; no language, no runtime and
      no operating system is assumed.

   *  Symmetric.  Either endpoint MAY call, publish and open a tunnel.
      The roles of initiator and responder exist only while the session
      is established and confer no other privilege.

   *  Sufficient for control traffic.  Commands and queries are calls,
      telemetry and alarms are events, and firmware, logs and media
      streams are tunnels; no fourth pattern is needed.

   *  Plain by default.  The core carries cleartext: it provides no
      confidentiality, no integrity and no per-frame verification, and
      it names no cipher.  A deployment that needs any of them adds one
      of two extensions, and the two are alternatives rather than
      layers: the frame-layer primitives of [RFC0009], which also
      define a longer header, or a secure transport that carries the
      whole session [RFC0010].  Adding either leaves every section of
      this document as it is.

   A deployment therefore narrows the protocol rather than extending
   it: a robot is integrated by publishing a descriptor and by
   implementing the profiles it needs, and this document is unchanged
   by the integration.

2.  Conventions

   The key words of [IETF-RFC2119] and [IETF-RFC8174] apply.  All
   multi-octet integers are in network byte order (big-endian) unless
   stated otherwise.  "Frame" denotes one complete protocol packet;
   "message" denotes the semantic entity carried by a frame.  Bits and
   bytes are numbered from zero.  Structured payloads are
   CBOR [IETF-RFC8949]; a conforming receiver MUST NOT reject a value
   merely because it uses a legal but non-canonical CBOR encoding.

3.  Frame Layer

3.1.  Header

   Every frame begins with a sixteen-octet header.  The structure of
   the header is shown in Table 1.

   +=======+=======+============+======================================+
   |Offset |Length |Field       |Description                           |
   +=======+=======+============+======================================+
   |0      |3      |magic       |The octets 0x4F 0x43 0x50 ("OCP")     |
   +-------+-------+------------+--------------------------------------+
   |3      |1      |version     |Protocol version; 0x01 in this        |
   |       |       |            |document                              |
   +-------+-------+------------+--------------------------------------+
   |4      |1      |type        |Message type (Section 5)              |
   +-------+-------+------------+--------------------------------------+
   |5      |1      |flags       |Flag bits (Section 3.2)               |
   +-------+-------+------------+--------------------------------------+
   |6      |2      |header_len  |Total length in octets of the header; |
   |       |       |            |0x0010 for the header of this document|
   |       |       |            |(Section 3.8)                         |
   +-------+-------+------------+--------------------------------------+
   |8      |4      |seq         |Sequence number, unsigned 32-bit      |
   |       |       |            |(Section 3.4)                         |
   +-------+-------+------------+--------------------------------------+
   |12     |4      |payload_len |Length in octets of the payload as    |
   |       |       |            |transmitted                           |
   +-------+-------+------------+--------------------------------------+

                         Table 1: Frame Header

   The header is packed: no field is padded, no octet is reserved and
   the payload begins at the octet named by "header_len".  The frame
   layout is shown in Figure 1.

         +-----------+-------------+------------------------+
         | header    | payload     | trailer (as agreed)    |
         | header_len| payload_len | none in this document  |
         +-----------+-------------+------------------------+

                         Figure 1: Frame Layout

   The magic octets and "header_len" let a receiver find the payload
   before it knows which extensions are in use, because "header_len" is
   at the same offset in every header form.  This document defines one
   form, of sixteen octets; [RFC0009] defines a longer one.

3.2.  Flag Bits

   The flag bits defined by this document are listed in Table 2.

   +=====+======+===========+==========================================+
   |Bit  |Name  |Scope      |Meaning                                   |
   +=====+======+===========+==========================================+
   |0x01 |F_ACK |per-frame  |The sender requests acknowledgement       |
   |     |      |           |(datagram transports; Section 7.2).       |
   +-----+------+-----------+------------------------------------------+
   |0x02 |F_COMP|session    |The payload is compressed (Section 3.5).  |
   +-----+------+-----------+------------------------------------------+
   |0x04 |F_AUTH|session    |This session is authenticated             |
   |     |      |           |(Section 6.2).                            |
   +-----+------+-----------+------------------------------------------+

                           Table 2: Flag Bits

   The two session-scope bits form the session flag set.  They are
   proposed in HELLO, confirmed as an intersection in WELCOME, and
   marked on each frame according to what was actually applied.  The
   per-frame bits are not negotiated.  A receiver MUST ignore flag bits
   it does not know.

   Bits 0x08 and above are not assigned here: they belong to the
   extensions of Section 3.8, of which [RFC0009] assigns the first
   three.  A session that uses that document reads the flag octet as one
   set of six bits.

3.3.  Limits and Negotiation

   Each endpoint states the largest payload it can receive in HELLO and
   WELCOME; the effective limit is the smaller of the two values, with
   a default of 1048576 octets.  A frame whose payload exceeds the
   effective limit MUST be rejected with E_PAYLOAD_TOO_LARGE.  The count
   is of payload octets only: neither the header nor a trailer added by
   an extension of Section 3.8 is counted.

   On a stream transport, frames are delimited solely by "payload_len";
   there MUST be no padding between frames.  On a datagram transport,
   one datagram carries exactly one frame.

3.4.  Sequence Numbers

   Each endpoint maintains its own 32-bit sequence space.  Every frame
   sent, including responses, increments the counter by one, modulo
   2^32.  Two numbers lie within one window of each other when the
   distance between them is less than 2^31, taken with the serial number
   arithmetic below.  A sender MUST NOT reuse a number while any number
   it has already sent in that session still lies within one window of
   it; an endpoint that is about to send the 2^31st frame of a session
   MUST close that session with BYE and open a new one rather than wrap
   around, since that is the point at which the numbers of the session
   meet again.

   Sequence numbers are compared with the serial number arithmetic of
   [IETF-RFC1982], which is defined for exactly this space: a number is
   before another when the difference of the two, taken modulo 2^32, is
   less than 2^31.  Sequence numbers are used for loss detection on
   datagram transports, for correlating acknowledgements, for log
   correlation, and, when [RFC0009] is in use, as part of the nonce of
   every frame.

3.5.  Compression

   When F_COMP is set, the payload is the compressed form of the CBOR
   value, produced with the compression algorithm agreed for the session
   (Section 3.6).  Compression is OPTIONAL per frame; an endpoint MAY
   compress only payloads that benefit from it.  A payload that cannot
   be decompressed with the agreed algorithm MUST be rejected with
   E_DECOMPRESS.

   Compression is applied before the primitives of [RFC0009] when those
   are used, so what they protect is the compressed octets.

3.6.  Algorithm Selection

   Compression takes an algorithm, named by a short string that the
   endpoints agree when the session is established (Section 6.1).  This
   document specifies the negotiation, not a set of algorithms: any name
   MAY be agreed by two endpoints that implement it, and the list below
   is an example; zstd is a common choice.  Compression is OFF by
   default and OPTIONAL: an endpoint that wants it lists at least one
   algorithm in HELLO.

   Some typical compression algorithms are shown in Table 3.

   +============+======================================================+
   |Name        |Method                                                |
   +============+======================================================+
   |zstd        |Zstandard [IETF-RFC8878]; a common choice             |
   +------------+------------------------------------------------------+
   |brotli      |Brotli [IETF-RFC7932]                                 |
   +------------+------------------------------------------------------+
   |deflate     |DEFLATE with a zlib wrapper [IETF-RFC1950]            |
   +------------+------------------------------------------------------+
   |gzip        |GZIP file format [IETF-RFC1952]                       |
   +------------+------------------------------------------------------+
   |lz4         |LZ4 frame format [LZ4-FRAME]                          |
   +------------+------------------------------------------------------+
   |xz          |LZMA2 in an .xz container [XZ-FORMAT]                 |
   +------------+------------------------------------------------------+
   |snappy      |Snappy block format [SNAPPY]                          |
   +------------+------------------------------------------------------+

                    Table 3: Compression Algorithms

   Names are compared as exact strings and are not registered: an
   endpoint MAY offer any name it implements, and the responder confirms
   a name only when it implements the same one with the same parameters.
   The parameters a name implies MUST be known to both endpoints before
   the name is offered.  A name defined outside this document SHOULD
   begin with "x-" while it is experimental.  Two endpoints that
   implement the same name differently MUST NOT agree on it; such a name
   is treated as one the responder does not implement.

   An endpoint offers the algorithms it is willing to use in the "algs"
   member of HELLO, most preferred first; the responder states the
   agreed algorithm in the same member of WELCOME.  An offer and the
   confirmation it produces, for example:

      "algs": {"comp": ["zstd", "deflate"]}

      "algs": {"comp": "zstd"}

   The member and its key are OPTIONAL.  Compression is OFF by default:
   an absent "comp" key and an empty array both mean that the endpoint
   offers no compression.  A name an endpoint does not recognise MUST be
   ignored in an offer and MUST NOT be confirmed.

   When the responder implements none of the algorithms offered, the
   F_COMP flag is not agreed and compression is not used.

   An endpoint MUST NOT apply an algorithm it did not offer, and MUST
   NOT apply one that WELCOME did not confirm.  A receiver that detects
   such a frame rejects it with E_UNSUPPORTED, or with E_DECOMPRESS when
   the mismatch is only visible while the payload is decoded.

   [RFC0009] adds the keys "enc", "itg" and "ztr" to the same member and
   specifies the algorithms they name.  An endpoint that does not
   implement that document ignores those keys in an offer, as it ignores
   any key it does not define.

3.7.  Streaming Parse

   On a stream transport a receiver accumulates octets and parses frames
   one at a time, reading "header_len" at offset six to find where the
   payload begins.  An incomplete frame is not an error: the receiver
   waits for more octets.  The payload length is explicit, so no escape
   mechanism is REQUIRED.

3.8.  Extension Points

   Three things may be added to the frame layer by another document of
   this series, and this document defines none of them.

   *  Flag bits.  Bits 0x08 and above of the flag octet are unassigned
      here.  A receiver MUST ignore a bit it does not know, so a
      primitive that marks itself on a frame is invisible to an endpoint
      that has not negotiated it.  [RFC0009] assigns 0x08, 0x10 and
      0x20.

   *  A longer header.  The value of "header_len" states how many octets
      precede the payload, so a longer header is parsed by the same code
      that parses this one, and the octets that follow offset sixteen
      are defined by the document that adds them.  A receiver that does
      not implement a header length it is offered rejects the session
      with E_UNSUPPORTED.  [RFC0009] defines a header of thirty-two
      octets.

   *  Trailers.  Octets MAY follow the payload.  Their number is fixed
      by the negotiated algorithm of the primitive that adds them and
      is never carried in the frame, so both endpoints know it from the
      negotiation.  This document defines none.

   An extension is negotiated in HELLO and WELCOME like any other
   session property (Section 6.1), and is applied to a frame only after
   it has been agreed.  A frame that carries a header form, a flag bit
   or a trailer that was not agreed is rejected with E_UNSUPPORTED.

   All of the security of the frame layer lives in these extensions.
   The primitives of [RFC0009] add confidentiality, integrity and
   per-frame verification to the frames themselves; [RFC0010] puts the
   whole session inside a secure transport instead.  This document
   carries cleartext.

4.  Value Layer

   The payload of a frame is exactly one CBOR value.  Every message of
   this document is a CBOR map, including the acknowledgement message,
   whose map carries a single member.  An empty payload decodes to null
   and never occurs in the flows defined here.

4.1.  One Value per Frame

   The payload octets, once the transforms of Section 3 have been
   reversed, are decoded as exactly one CBOR value.  A payload is never
   a concatenation of values and never a CBOR sequence: the header
   already delimits the payload by payload_len, so no self-delimiting
   sequence is needed and a decoder MUST NOT read past the declared
   length.

   A payload of zero octets decodes to null.  A receiver that obtains
   null from a frame whose type is defined to carry a map MUST treat
   the frame as malformed (Section 4.5).

4.2.  Value Types

   Table 4 lists the CBOR types used by this document, the notation
   used for them here, and what each of them carries.

   +============+=================+====================================+
   |CBOR type   |Notation         |Used for                            |
   +============+=================+====================================+
   |unsigned    |1024             |identifiers, sequence numbers,      |
   |            |                 |offsets, lengths, error codes       |
   +------------+-----------------+------------------------------------+
   |negative    |-1024            |signed quantities                   |
   +------------+-----------------+------------------------------------+
   |byte string |h'DEADBEEF'      |opaque octets: bus frames, tunnel   |
   |            |                 |slices, nonces, MACs                |
   +------------+-----------------+------------------------------------+
   |text string |"device.event"   |names: member keys, topics,         |
   |            |                 |procedures, tunnels, bus names      |
   +------------+-----------------+------------------------------------+
   |array       |["rpc","pubsub"] |ordered lists of names and records  |
   +------------+-----------------+------------------------------------+
   |map         |{"ok": true}     |one message; records; arguments     |
   +------------+-----------------+------------------------------------+
   |boolean     |true, false      |success, half close, destruction    |
   +------------+-----------------+------------------------------------+
   |null        |null             |a defined member with no value      |
   +------------+-----------------+------------------------------------+
   |float       |3.1415926        |timestamps and measurements         |
   +------------+-----------------+------------------------------------+

                          Table 4: Value Types

   Byte strings are written in this document with the CBOR diagnostic
   notation h'...'.  OCP defines no CBOR tags of its own.  Where a
   value's meaning is a kind a standard CBOR tag names, a sender MAY
   wrap the value in that standard tag from [IETF-RFC8949]; the tag is
   OPTIONAL and supplementary and carries no data of its own.
   A receiver MUST accept a value with or without a standard tag and
   MUST ignore any tag it does not understand; it MUST NOT reject a
   frame merely because a value is tagged or untagged.

   Member keys are text strings and are compared as exact octet
   sequences: a receiver MUST NOT fold case, trim space or apply any
   other normalisation to a key, and MUST NOT treat two keys that
   differ only in case as the same member.  The single exception is the
   "args" member of CALL, whose keys MAY be unsigned integers (Section
   5.3); those integers are positions and not names, and the rule above
   applies to the text keys of that map and not to its integer keys. The
   two forms MAY stand in one map, and a key is never folded from one
   form into the other.

   An integer used as an identifier, offset, length or code is unsigned
   unless the definition of the member says otherwise.

4.3.  Members

   Every message is a map so that the format can grow: a later revision
   can add a member without changing the meaning of a frame, and a
   member that has a default can be omitted.  An array would bind
   meaning to position and could not be extended.  The rules for
   members are:

   *  A member marked OPTIONAL MAY be omitted.  An omitted member is
      absent; it is not the same as a member present with the value
      null.

   *  A receiver MUST ignore a member it does not define.

   *  A sender MUST NOT give a member a value of a type other than the
      type defined for it, and MUST NOT send a member whose meaning it
      does not know.

   *  A receiver MUST NOT require a member that this document marks
      OPTIONAL, and MUST NOT derive meaning from the order of the
      members, which CBOR does not preserve.

4.4.  Common Payload Forms

   Four shapes cover every message of this document.

   1.  Argument map: a map whose keys carry the arguments, each under
       either the name of a parameter or its position.

          {"id": 7, "name": "drive", "args": {"left": 1000,
              "right": -1000}}
          {"id": 7, "name": "drive", "args": {0: 1000, 1: -1000}}

       Which keys may appear, and what the values mean, are fixed by the
       procedure, not by this document.

   2.  Nested record: a map that describes one object and is carried as
       the value of a member, as a member of another map, or as an
       element of an array.

          {"topic": "device.event", "data": {"name": "frame",
              "data": {"addr": 42, "octets": h'DEADBEEF'}}}

   3.  Answer: a map that carries either a value or an error, never
       both.

          {"id": 7, "ok": true, "value": null}
          {"id": 8, "ok": false, "error": {"kind": "HardwareError",
              "message": "command rejected"}}

   4.  Error object: a map with "code" and "message", used by the ERROR
       message and by the state message of a tunnel.

          {"code": 3, "message": "checksum mismatch"}

   When a payload is written for a new message or a new profile, the
   following conventions apply:

   *  Use a map at the top level, and wherever a receiver has to pick
      one member out of several, as in an argument map.  Use an array
      only for a homogeneous list whose order is part of its meaning,
      as in the capability list of HELLO.

   *  Use a byte string for anything that is opaque octets.  Never
      carry octets as a text string and never encode them into text,
      since a byte string carries them exactly and without expansion.

   *  Omit a member rather than send it empty.  Send null only where
      this document defines it, as in the "value" member of a
      successful call that returns nothing.

   *  Use integers, not floats, for counts, offsets, lengths,
      identifiers and codes.  A float is appropriate only for a
      measurement whose precision is inherently limited.

   *  Encode numeric values at 64-bit width: unsigned and negative
      integers as the 8-octet form, and floats as [IEEE754] double; this
      is a recommendation and not a requirement; a sender MAY use a
      narrower legal form, and a receiver MUST still accept any legal
      CBOR width, as Section 2 requires.

   *  Keep a payload small.  The negotiated limit (Section 3.3) bounds
      the octets of one frame, and a value that can be large belongs in
      a tunnel (Section 10).

4.5.  Decoding Order

   A receiver reverses the transforms of Section 3 before it decodes
   the value:

   1.  Compression: decompress the payload (Section 3.5); a failure is
       E_DECOMPRESS.

   2.  Value: decode one CBOR value; a failure is E_BAD_PAYLOAD.

   The primitives of [RFC0009], when they are in use, precede these two
   steps, so a frame whose integrity or cipher check fails never
   reaches the decompressor and a decoder is never asked to parse
   octets whose origin is not established.  A value-level failure is
   E_BAD_PAYLOAD; the frame is discarded and the session continues,
   since a bad payload is the fault of one frame and not of the
   session.

   A decoder MUST NOT reject a value merely because it uses a legal but
   non-canonical CBOR encoding (Section 2).

4.6.  Semantic Tags

   OCP defines no protocol-specific CBOR tags of its own.  Where a
   value's meaning is a kind that a standard CBOR tag names, a sender
   MAY wrap the value in that standard tag from the IANA CBOR Tags
   registry [IETF-RFC8949]; the tag is OPTIONAL and supplementary and
   carries no data of its own.  The principal case in this document is a
   timestamp: a float that denotes a point in time MAY be tagged 1
   (epoch-based date/time), or, if the time is expressed as an RFC 3339
   string, tagged 0 (standard date/time string).  A measurement that is
   not a time has no applicable standard tag and is sent untagged.

   Every other field of this document has a fixed CBOR type and no
   applicable standard tag, so it is sent untagged; a sender SHOULD NOT
   add a tag to such a field, and a receiver MUST ignore any tag it
   finds on one.

   The rules for a receiver are:

   *  A receiver MUST accept a value whether or not it carries a
      standard CBOR tag.

   *  A receiver MUST ignore any tag it does not understand, in the
      manner of [IETF-RFC8949]; the tag alone is never a reason to
      reject.  An implementation that does not use tags, such as OCP Air
      [RFC0011], simply strips and ignores any tag it meets and decodes
      the inner value; this is always permitted and such an
      implementation remains conformant.

   *  A receiver MUST NOT derive meaning from the presence or absence of
      a tag and MUST NOT reject a frame for either reason.

   *  A malformed inner value is still reported with E_BAD_PAYLOAD; the
      tag is never the cause of rejection.

5.3.  CALL

      {"id": 7, "name": "drive", "args": {"left": 1000, "right": -1000}}
      {"id": 7, "name": "drive", "args": {0: 1000, 1: -1000}}
      {"id": 7, "name": "drive", "args": {0: 1000, "right": -1000}}

   The identifier is an unsigned 32-bit value chosen by the caller and
   MUST NOT be reused while a response is outstanding; wrapping is
   permitted.  A request for a name that is not known is answered with
   an application error in RESULT, not with an ERROR frame.  Either
   endpoint MAY send CALL, and the receiver MUST answer with RESULT.

   "args" is a map and not an array, so that a call can bind a value to
   a name as well as to a position, and so that a procedure can gain a
   parameter without changing the meaning of one that exists.  A key
   says how the value after it is bound:

   *  A text key carries one named argument.  The key is the name of the
      parameter and is compared exactly, as member keys are (Section
      4.3).

   *  An unsigned key carries one positional argument.  Positions count
      from zero among themselves: the unsigned keys of a well-formed map
      are exactly the integers from 0 to n-1, where n is the number of
      positional arguments in that map, whatever named arguments stand
      beside them.  A gap, a key that repeats and a key beyond n-1 each
      leave the map malformed.

   The two forms MAY appear in one map and this document ranks neither
   above the other: every key binds one value, whether the caller named
   it or counted it, and one call MAY carry some arguments named and
   others positional.  The protocol draws the line at the shape of the
   map and no further: which keys a procedure accepts, whether it takes
   one form or the other or a mix of both, and what it does when two
   keys claim one parameter are decided by the procedure and not here.
   That answer belongs to discovery (Section 9.1), it is not negotiated,
   and a handler rejects what it does not accept with an application
   error in RESULT.

6.  Session Establishment and Lifetime

6.1.  Session Flag Negotiation

   1.  The initiator lists the session flags it wants in HELLO: the
       authentication bit if it will authenticate and the compression
       bit if it wants compression.  For compression it lists the
       algorithms it is willing to use in the "algs" member
       (Section 3.6).  An extension of Section 3.8 adds its own member
       to the same message and is negotiated by the same exchange;
       [RFC0009] states the one it adds.

   2.  The responder answers with the intersection of the proposed bits
       and the bits it supports, in WELCOME, and with one compression
       algorithm: the first entry of the initiator's list that it also
       implements.  When the member or its key is absent, no algorithm
       is agreed and the F_COMP flag is cleared.

   3.  The agreed set is the WELCOME value.  Each frame thereafter marks
       the bits it actually applies.  Compression MAY vary per frame;
       authentication and every agreed extension apply to the whole
       session.

   4.  A transform whose offers have no algorithm in common is not
       agreed and its flag is cleared; the initiator proceeds without
       it.

   5.  A frame MUST NOT set F_AUTH unless authentication succeeded, and
       MUST NOT set a flag bit, a header length or a trailer that the
       agreement does not cover.  Such a frame is rejected with
       E_UNSUPPORTED.

   6.  An initiator that requires an extension that WELCOME does not
       confirm MUST close the session rather than continue without it.
       Which extension is required, if any, is deployment policy.

6.2.  Optional Authentication

   The "auth" member of HELLO is OPTIONAL.  When it is present it is a
   map whose "method" member names one authentication method by a
   string.  Every other member of that map is defined by the method and
   is opaque to this document: the protocol itself reads "method" and
   nothing else.

   In HELLO the "auth" map carries the initiator's credential:

      {"method": <text>, ... method-specific members ...}

   In WELCOME the "auth" map carries the result of the handshake:

      {"ok": <bool>, ... method-specific proof ...}
      {"ok": false, "error": {"code": <uint>, "message": <text>}}

   "ok" is REQUIRED.  "true" means the handshake succeeded and the
   session proceeds; "false" means it failed, in which case "error"
   names the reason and the session is closed with E_UNAUTHORIZED.  A
   method that defines no proof leaves only "ok" (and, on failure,
   "error").  The members a method defines MUST be known to both
   endpoints before the method is used (Section 6.2).

   The responder fails the handshake, closing with E_UNAUTHORIZED,
   when it requires authentication but the initiator presented none,
   when it does not implement the method, when the credential does
   not verify, and when it cannot use the key material the method
   yields.  Silent downgrade to an unauthenticated session is
   prohibited.

   The exchange is shown below.

      Initiator                                  Responder
         |---- HELLO {auth: {method, ...}} ----->|
         |<--- WELCOME {auth: {ok, ...}} --------|
         |         (otherwise E_UNAUTHORIZED)     |

   Any method MAY be used.  This document does not define a set of
   methods, does not register their names, and does not constrain how
   an identity is proved.  A shared secret, a keyed MAC, a digital
   signature, a certificate chain, a ticket issued out of band and a
   method that carries no credential at all are equally admissible. A
   name is compared as an exact string.  What a name implies, that is,
   the members it uses, the credential it carries, the proof it returns
   and the keys it yields, MUST be known to both endpoints before the
   name is used.  A name defined outside this document SHOULD begin with
   "x-" while it is experimental.  Two endpoints that implement the same
   name differently MUST NOT agree on it; such a name is treated as one
   the responder does not implement.

   The choice belongs to the initiator and is not negotiated.  The
   responder either accepts the named method or fails; it MUST NOT
   answer with another method of its own choosing and MUST NOT offer a
   list for the initiator to choose from.

   A method MAY do three things, and the first is its purpose:

   1.  Authenticate the initiator to the responder, by verifying the
       credential the method carries.

   2.  Return a proof in the "auth" member of WELCOME, which
       authenticates the responder to the initiator.  The initiator
       MUST verify the proof when the method defines one; a method that
       defines no proof is complete once the responder has accepted the
       credential.

   3.  Yield key material.  A method MAY yield a master secret.  This
       document never uses one; [RFC0009] specifies the keys that are
       derived from it, the session properties that require it and the
       rules for rotating it.  A method that yields no secret is
       complete for every purpose of this document.

   Two methods are given below as examples.  Neither is required and an
   implementation MAY ignore both.

   *  "hmac": a mutual challenge-response over a shared secret.  The
      initiator sends a nonce and a MAC over it; the responder answers
      with a nonce of its own and a MAC over both nonces, which the
      initiator MUST verify.  The "auth" map uses the same shape as
      Section 6.2: the HELLO map carries "method", "nonce" and "mac";
      the WELCOME map carries "ok", the responder nonce and its MAC.

         HELLO   {"method": "hmac", "nonce": h'...', "mac": h'...'}
         mac = HMAC-SHA256(secret, "OCP-HELLO" || client || nonce)
         WELCOME {"ok": true, "nonce": h'...', "mac": h'...'}
         mac = HMAC-SHA256(secret, "OCP-WELCOME" ||
              client_nonce || server_nonce)

      "nonce" is at least 16 octets of unpredictable data.  The single
      shared secret therefore authenticates both ends without being
      revealed.

   *  "token": a bearer ticket presented once, with no responder proof.
      The HELLO map carries "method" and "ticket"; on success WELCOME
      carries only "ok", and on failure "ok" is false with an "error":

         HELLO   {"method": "token", "ticket": h'...'}
         WELCOME {"ok": true}
         WELCOME {"ok": false, "error": {"code": 13, "message": "bad"}}

      A rejected ticket closes the session with E_UNAUTHORIZED.

   The key material a method yields, when it yields any, is used by
   [RFC0009] and by nothing in this document: that document derives the
   per-direction keys from it, states which properties require it and
   gives the rules for rotating it.  An endpoint that does not use that
   document ignores the secret entirely, and an endpoint that offers no
   method at all is unaffected by this paragraph.

6.3.  Lifetime

   The lifetime of an OCP session is shown in Figure 2.

   Initiator                            Responder
       |  transport connect                 |
       |---- HELLO ------------------------>|  first frame MUST be
       |                                    |  HELLO
       |<--- WELCOME -----------------------|  session established
       |  (OPTIONAL) CALL ping              |  heartbeat
       |  (OPTIONAL) CALL metadata          |  metadata
       |---- CALL ------------------------->|  RPC
       |<--- RESULT ------------------------|
       |---- (OPTIONAL) SUBSCRIBE --------->|  subscribe to a topic
       |<--- (OPTIONAL) EVENT --------------|  events from the topic
       |---- (OPTIONAL) UNSUBSCRIBE ------->|
       |<--- (OPTIONAL) ERROR --------------|  some error
       |---- (OPTIONAL) TUNSTAT / TUNDATA-->|  tunnel traffic
       |<--- (OPTIONAL) TUNSTAT / TUNDATA --|
       |---- BYE -------------------------->|
       |  transport close                   |

                  Figure 2: Lifetime of an OCP session

   Reconnection establishes a new session.  A responder MUST NOT require
   state from a previous session; the session identifier is for
   correlation only.  Resumption of a byte stream across sessions is an
   application concern and is expressed with the tunnel offset field
   (Section 10).

   An endpoint MUST enforce an abandonment timeout on every session.  A
   timer for the peer is started when the session is established and is
   reset whenever any frame is received from the peer, whatever that
   frame is: HELLO, WELCOME, CALL, RESULT, EVENT, SUBSCRIBE, TUNDATA,
   TUNSTAT, ACK, BYE and ERROR all count, and a RESULT counts even when
   it answers a call the caller has stopped waiting for.  A frame that
   the endpoint sends does not reset the timer; only one received from
   the peer does.  If no frame from the peer is received for a
   continuous period of T, the endpoint MUST forcibly and abnormally
   close the session's transport.

   The close is silent.  The endpoint MUST NOT send BYE, ERROR or any
   other frame to the peer, and MUST NOT wait for an acknowledgement; it
   simply drops the transport; the purpose is to free resources that
   would otherwise be held forever, and to resolve a half-open session
   left by a peer that vanished without sending BYE (Section 5.10).

   T is an implementation parameter; a RECOMMENDED default of fifteen
   seconds stands in Table 18 and matches the heartbeat liveness timeout
   of Section 6.7.  An endpoint that needs longer idle periods MUST keep
   the timer reset by sending heartbeats (Section 6.7) or any other
   frame, and it is only ever a frame received from the peer -- the
   answer to a heartbeat, or any other frame at all -- that resets it.
   The timeout is independent of, and complementary to, the graceful BYE
   close: a peer that leaves cleanly sends BYE, and the timeout only
   applies once the peer has gone silent.

   The timeout is not cancelled by outstanding calls.  A session whose
   calls are all answered but which then hears nothing times out; a
   session with calls still awaiting answers that hears nothing also
   times out.

6.4.  Remote Procedure Call

   Either endpoint MAY originate a call.  The members are listed in
   Sections 5.3 and 5.4; this section describes how they are used.

6.4.1.  The Exchange

   The exchange is shown in Figure 3.

            Caller                                    Callee
               |---- CALL {id, name, args} ------------->|
               |<--- RESULT {id, ok, value | error} -----|

                   Figure 3: A Remote Procedure Call

   1.  The caller chooses an identifier that is free in its own
       direction, that is, one that no call whose answer has not
       arrived is using, and sends CALL with the procedure name and the
       arguments.

   2.  The receiver looks up the name and executes what it names.  It
       answers once, with RESULT carrying the same identifier and either
       "ok" set to true together with the returned value, or "ok" set to
       false together with an "error" object.

   3.  The caller matches the answer to the call by the identifier.

   4.  Heartbeats and discovery travel this path too: they are calls to
       "ping" and to "metadata" (Sections 6.7 and 9.1).

6.4.2.  Answers and Failures

   *  Exactly one RESULT is sent per CALL, whether the procedure
      succeeded, failed or does not exist.  A caller never waits for a
      second answer and never reassembles one.

   *  A success carries the returned value in "value"; a procedure that
      returns nothing answers with null.  A failure carries an "error"
      object; the two never appear in one RESULT.

   *  An unknown procedure, a form of arguments the procedure does not
      accept, a name it does not define, a wrong number of arguments and
      a failure inside the procedure are all answered in RESULT and MUST
      NOT be answered with ERROR (Section 5.11): what is in question is
      the call, not the session.

   *  A procedure name is compared exactly, and so is the key of a named
      argument.  An absent "args" and an empty map mean the same.  Which
      keys a procedure accepts, whether named ones, positional ones or a
      mix of the two, is fixed by the procedure and not by this
      document: nothing here forbids a caller from mixing the forms, and
      how a handler reads such a map, including one in which two keys
      claim one parameter, is decided by the handler and answered in
      RESULT.

   *  A RESULT whose identifier matches no outstanding call MUST be
      ignored.  This is what makes a late answer harmless.

6.4.3.  Identifiers

   *  Each direction has its own identifier space; identifiers are
      unsigned 32-bit values and wrapping is permitted.

   *  An identifier MUST NOT be reused while its call is outstanding.
      Once the answer has arrived, the identifier is free again.

   *  Subscriptions draw from the same space (Section 5.6), so the
      answer to a subscription can never be mistaken for the answer of a
      call and one table of outstanding requests is enough.

6.4.4.  Order, Concurrency and Time

   *  Several calls MAY be outstanding at once; this document does not
      bound how many.  An endpoint MAY defer an answer.

   *  Answers MAY arrive in any order.  A caller that needs an order
      MUST wait for one answer before sending the next call.

   *  Nothing bounds how long an answer may take, and no cancellation is
      defined.  A caller that abandons a call ignores the RESULT when it
      arrives.

6.5.  Publish and Subscribe

   Either endpoint MAY publish and either MAY subscribe; the two roles
   are independent of each other and of the roles of Section 6.1.  The
   members are listed in Sections 5.5 to 5.7; this section describes how
   they are used.

6.5.1.  The Exchange

   The exchange is shown in Figure 4.

        Subscriber                                Publisher
            |---- SUBSCRIBE {id, topic} ------------->|
            |<--- RESULT {id, ok: true} --------------|
            |<--- EVENT {topic, data} ----------------|  repeat
            |---- UNSUBSCRIBE {id, topic} ----------->|
            |<--- RESULT {id, ok: true} --------------|

                Figure 4: A subscription and its events

   1.  A subscriber sends SUBSCRIBE with the topic name and OPTIONALLY
       an identifier from the space it uses for calls.

   2.  The publisher adds the topic to the session and answers with
       RESULT, "ok" set to true and no value.

   3.  From then on the publisher sends EVENT for each filter held by
       the session, and on no concrete topic no filter matches.

   4.  UNSUBSCRIBE removes the topic.  Events already in flight MAY
       still arrive.

6.5.2.  Subscribing

   *  SUBSCRIBE and UNSUBSCRIBE are answered with RESULT exactly as a
      call is, and their identifier comes from the same space
      (Section 6.4.3).  The value of a successful answer is null.

   *  Subscribing to the same filter twice is idempotent and MUST NOT
      cause duplicate deliveries; two distinct filters that both match a
      topic are independent, and each MAY deliver the event it matches.

   *  UNSUBSCRIBE succeeds even when the topic was not subscribed: a
      subscription is only ever removed, never refused.

   *  A subscription belongs to one session and does not survive a
      reconnect: the new session subscribes again.

   *  A SUBSCRIBE or UNSUBSCRIBE carries a topic filter, not always a
      concrete topic; a published event always carries a concrete topic
      (Section 5.5).  The filter MAY contain MQTT-style wildcards, and
      topic levels are separated by ".":

      -  "+" matches exactly one level.  "device.+" matches
         "device.event" and "device.fault", but not "device" nor
         "device.event.foo".

      -  "#" matches the current level and every level after it; it MUST
         be the last level and the only character in that level.
         "device.#" matches "device", "device.event" and
         "device.event.foo"; a bare "#" matches every topic.

      -  A level that is neither "+" nor "#" is matched literally,
         character for character; a "+" or "#" inside a level is a
         literal character, not a wildcard.  A filter has no way to
         escape either one, so "device.f+oo" matches only the topic
         "device.f+oo" and never "device.foo", and "device.a#b" matches
         only itself.

      The namespaces are listed in Section 9.2; a wildcard filter is
      accepted even when it currently matches no assigned topic.

6.5.3.  Delivery

   *  An event is delivered only to sessions that hold a filter matching
      its topic (Section 6.5.2), and only after that filter's
      subscription has been answered.

   *  A retained event (EVENT with "retain" true, Section 5.5) is stored
      by the publisher as the single retained message of its topic, and
      replaces any prior retained message of that topic.  A retained
      event with no payload clears that retained message.  When a
      subscription is answered, the publisher immediately delivers the
      retained message of every concrete topic the new filter matches,
      before any later publication; a pseudo-topic (Section 9.2.1)
      carries no retained message (Section 9.2.1).

   *  On a reliable transport the events of one topic are delivered in
      the order they were published.  The events of different topics MAY
      interleave in any order, and so may an event and the answer of a
      call.

   *  An event carries no identifier and is never answered: there is no
      RESULT, no ERROR and no acknowledgement at this level, whatever
      the transport does underneath.  A receiver MUST NOT send anything
      in reply to an event.

   *  Delivery is best effort.  A publisher cannot learn whether a
      subscriber received an event; a consumer that cannot afford to
      recovers by asking for the present state with a call, which is
      what the core profile of Section 9.1 is for.

   *  The payload, when there is one, is carried in "data"; its shape
      belongs to the topic and not to this document.

6.6.  The Blob Tunnel

   The blob tunnel carries raw byte streams, for example firmware
   images, media streams, log uploads and vendor extensions.  Several
   tunnels MAY exist on one session at a time, distinguished by name.
   The tunnel defines no compression and no protection of its own: those
   are provided by the frame layer (Sections 3.5 and 3.8) and therefore
   apply to tunnel traffic as they apply to every other message.

6.6.1.  Messages

   Either endpoint MAY open a tunnel.  The exchange is shown in
   Figure 5.

         Opener                                     Peer
            |---- TUNSTAT {tun, open: {}} ----------->|
            |<--- TUNSTAT {tun, open: {ok: true}, ----|
            |             ack, window}                |
            |---- TUNDATA {tun, off, data} ---------->|  repeat
            |<--- TUNSTAT {tun, ack, window} ---------|
            |---- TUNDATA {tun, off, data, eof} ----->|
            |<--- TUNSTAT {tun, close: true} ---------|

         Figure 5: A tunnel, from establishment to destruction

   The members are listed in Sections 5.8 and 5.9.  TUNDATA carries a
   slice of the stream; TUNSTAT carries everything else: establishment,
   progress, flow control, retransmission, half close, destruction and
   tunnel errors.  One state frame MAY carry several members at once,
   so that an acknowledgement, a window update and an end-of-stream
   marker can be sent in one frame.  A state frame is never answered
   with a RESULT: this primitive answers state with state.

6.6.2.  Establishment

   1.  Either endpoint sends TUNSTAT with "open" set to an empty map,
       and MAY include its receive window and its starting offset.

   2.  The peer either accepts, answering TUNSTAT with "open" set to
       {"ok": true} plus its acknowledgement and window, or refuses,
       answering {"ok": false} plus an error.

   3.  Data or state received for a tunnel that is not established MUST
       be answered with E_NO_TUNNEL; the receiver MUST NOT discard it
       silently.

   4.  Both directions share the tunnel, and each has its own offsets,
       its own acknowledgement and its own end-of-stream marker.  A
       direction MAY therefore be finished on its own (Section 6.6.5);
       only "close" ends the tunnel itself (Section 6.6.6).

6.6.3.  Data and Flow Control

   TUNDATA carries a slice at offset "off".  TUNSTAT reports the
   receiver's view of the stream: the acknowledgement "ack", the receive
   window "window", and OPTIONALLY a request pointer "off".

   Acknowledgement and window.  "ack" is the number of contiguous octets
   received in order; every octet below "ack" has been received and the
   next octet wanted is at "ack".  "window" is the number of octets the
   sender MAY still have in flight (sent but not yet acknowledged).  The
   sender MUST keep

      in_flight <= window,
      where in_flight = (highest offset sent) - ack

   or, equivalently, it MUST NOT send a slice that lies beyond
   "ack + window".  The receiver derives "window" from its free buffer
   and advertises it as bytes are consumed; a zero window halts the
   sender until it grows again.  A receiver that has advertised a zero
   window MUST send a TUNSTAT of its own as soon as the window grows,
   since the sender that the zero stopped sends nothing and nothing else
   would prompt the receiver to speak again: the two would otherwise
   wait for each other.  At any other time updates MAY be coalesced into
   one frame.

   Sending.  The sender slices the stream; the RECOMMENDED slice size is
   8192 octets (Table 18).  It transmits slices whose offset lies in the
   half-open interval [ack, ack + window), retains each until it is
   acknowledged, and waits for a state frame once the window is full.

   Receiving.  The receiver places each slice by its "off", advances
   "ack" across the new contiguous prefix and holds any out-of-order
   octets.  It sends TUNSTAT with the current "ack" and "window" as
   needed, and MAY coalesce updates into one frame.  Duplicate
   or overlapping slices are trimmed; octets below "ack" are ignored.

   The window is shown in Figure 6.

      received & delivered : 0 ......... ack
      in flight (unacked)  : [  up to "window" octets  ]
      may still be sent    : ack .................. ack + window

               Figure 6: The BlobTun sliding window

6.6.4.  Retransmission and Resumption

   Retransmission.  When the receiver has delivered up to "ack" but the
   next octet, at offset "ack", is missing, it sends TUNSTAT with "off"
   set to "ack" -- a request to (re)transmit from that offset.  The
   sender MUST resend from "off" while it still holds the data, and MUST
   answer E_TUNNEL_RESET when the requested octets have already been
   released.  A receiver SHOULD throttle gap notifications (Table 18).

   Resumption.  A receiver that restarts MAY open a tunnel with "off"
   set to the octets it already holds; the sender continues from there.
   The application MAY instead ignore offsets and treat the
   tunnel as a best-effort stream.

6.6.5.  Half Close

   TUNSTAT with "eof" set announces that one direction is finished; the
   other direction MAY continue.  A receiver of an end-of-stream marker
   with no buffered data observes the end of the stream.

6.6.6.  Destruction

   TUNSTAT with "close" set destroys the tunnel at both endpoints
   immediately, discarding anything not yet consumed; the name becomes
   reusable.  No answer is REQUIRED.  A close for an unknown tunnel is
   processed silently so that closings cannot ping-pong.  Data that
   arrives for a destroyed tunnel is answered with E_NO_TUNNEL.

6.7.  Heartbeat and Metadata

   A heartbeat is one call to the core instruction "ping" with the
   sender's current time:

      CALL   {"id": 5, "name": "ping", "args": {0: 1726723200.125}}
      RESULT {"id": 5, "ok": true,
              "value": {"t": 1726723200.125, "time": 1726723200.126}}

   The "t" member echoes the request and "time" is the responder's wall
   clock.  Either endpoint MAY originate a heartbeat, and a receiver
   MUST answer a ping call.  A RECOMMENDED interval is five seconds,
   with a liveness timeout of fifteen seconds (Table 18); both are
   application policy.  An endpoint that detects liveness failure closes
   the session as Section 6.3 directs.

   Metadata is one call to the core instruction "metadata" (Section
   9.1), which reports what the responder offers: its procedures, its
   sensors, its actuators, its parameters and its events.  An initiator
   SHOULD call it once after establishing a session and cache the
   result.  When what the responder offers changes it SHOULD publish the
   fact on the "core.metadata" topic, and a consumer that sees it MUST
   read metadata again rather than go on using what it cached.

7.  Transport Bindings

7.1.  Stream Transport

   Frames are written back to back with no padding.  A receiver reads a
   header, then the announced payload and OPTIONAL trailer.

7.2.  Datagram Transport

   One datagram carries exactly one frame, and each frame is processed
   on its own.  A sender MAY request acknowledgement for important
   frames by setting F_ACK, and MAY retransmit with the same sequence
   number on timeout; a receiver SHOULD deduplicate retransmissions by
   sequence number alone, which names one transmission and not one
   frame: a retransmission repeats the octets of the frame it repeats,
   and with them its type.  Frames whose loss is tolerable need not
   request acknowledgement.  A single frame, including header and
   trailer, SHOULD NOT exceed 1200 octets so as to avoid fragmentation.
   Bulk data SHOULD use a stream transport together with the tunnel
   primitive.

   Session establishment is not a property of the transport: HELLO and
   WELCOME are ordinary frames and MAY be carried by datagrams.  The
   handshake proceeds as in Section 6, with two additions:

   *  The initiator MAY repeat HELLO, with the same sequence number,
      until WELCOME arrives.  A responder MUST treat a repeated HELLO
      as the same request and SHOULD answer it with the same WELCOME,
      under the same sequence number it used before.

   *  Either endpoint MAY abandon a datagram session that has carried
      no frame for an application-defined interval; the next datagram
      then opens a new session with a new HELLO.

   Authentication (Section 6.2) applies to a datagram session exactly
   as it applies to a stream session and requires no lower layer to
   provide it.  Three points are particular to an unreliable transport:

   *  A frame carries everything needed to process it: its length is in
      the header and, when [RFC0009] is in use, its nonce material is in
      the extended header, so no frame depends on another and a lost
      frame does not make the frames that follow it undecodable.

   *  A retransmission carries the same octets as the frame it repeats,
      and therefore the same length and the same nonce material.
      Accepting it twice changes nothing, which is what the
      deduplication above already prevents.

   *  A receiver SHOULD reject a frame whose sequence number it has
      already accepted, unless the octets are identical to the frame it
      accepted under that number, so that a recorded frame cannot be
      replayed into an authenticated session.

   Confidentiality and integrity are not provided by this document.  A
   datagram session that needs them uses the primitives of [RFC0009] or
   a secure transport [RFC0010]; neither changes any rule above.  The
   octet budget above is counted after any trailer of Section 3.8, so
   enabling one leaves less room for payload.

7.3.  Other Transports

   The protocol makes no assumption about the octet transport.  A new
   binding only has to provide delimited frames and to state whether the
   transport is reliable.

7.4.  Recommended Port and URI Scheme

   The RECOMMENDED port for a TCP or a UDP binding is 6286.  The digits
   are a mnemonic: on a telephone keypad the letters of the sixth, the
   second, the eighth and the sixth key spell O, C, T and O.  The number
   is a convenience and not a requirement.  A deployment MAY use any
   port, and an endpoint learns the port of its peer from configuration
   or from service discovery, never from the protocol itself.  The value
   is not registered with IANA.

   One URI scheme is used for a session of this document, by
   configuration files, by tools and by logs [RFC0007].  It is not part
   of the protocol and no endpoint parses one at run time.

      ocp://host[:port]      cleartext; port defaults to 6286

      The host is an IPv4 or IPv6 address, or a host name.

9.  Service Profiles

9.1.  Core Profile

   +============+=========================+============================+
   |Instruction |Signature                |Meaning                     |
   +============+=========================+============================+
   |ping        |(t) -> {t, time}         |Heartbeat (Section 6.7).    |
   +------------+-------------------------+----------------------------+
   |status      |() -> {state, time,      |The state of the peer       |
   |            |uptime, fault, message}  |(Section 9.1.1).            |
   +------------+-------------------------+----------------------------+
   |metadata    |() -> {instructions,     |What the peer offers        |
   |            |sensors, actuators,      |(Section 9.1.2).            |
   |            |params, events}          |                            |
   +------------+-------------------------+----------------------------+
   |sense       |(name) -> value          |Reads one sensor            |
   |            |                         |(Section 9.1.3).            |
   +------------+-------------------------+----------------------------+
   |actuate     |(name, ...) -> null      |Operates one actuator       |
   |            |                         |(Section 9.1.3).            |
   +------------+-------------------------+----------------------------+
   |get_param   |(name) -> value          |Reads one device parameter  |
   |            |                         |(Section 9.1.3).            |
   +------------+-------------------------+----------------------------+
   |set_param   |(name, value) -> null    |Writes one device parameter |
   |            |                         |(Section 9.1.3).            |
   +------------+-------------------------+----------------------------+

                  Table 20: Core Profile Instructions

9.1.1.  The State of a Peer

   "status" answers a map and not a string, because a program has to be
   able to act on what it reports:

      {"state": "ready", "time": 1726723200.126, "uptime": 42.5,
       "fault": null, "message": null}

   "state" is one of "ready", "busy", "fault" and "offline"; a peer that
   has nothing better to say reports "ready" while it is answering
   calls.  "time" is the wall clock of the peer and "uptime" running
   time in seconds.  "fault" names the latched fault of Section 9.2.4
   when there is one and is null otherwise; "message" is a text meant
   for a human, or null.  A consumer MUST ignore a member it does not
   define.

9.1.2.  Metadata

   "metadata" reports what the peer offers, in one call and in one
   shape, so that a program needs no other discovery mechanism.  Its
   value is a map with five members.  Each is an array, each is
   OPTIONAL, and a peer that offers none of a kind returns an empty
   array rather than omitting the member.

   instructions  [{name, args, memo}]: the procedures this peer serves.
      An instruction of Table 20 MAY be listed here and MAY be left out:
      those of the core profile are served whichever way they are
      listed, and nothing in this member changes what one of them does.
      A caller therefore MUST NOT read the absence of a name, including
      one of Table 20, as a claim that the procedure is not served, and
      MUST NOT read its presence as a claim that anything more is
      offered.

   sensors  [{name, type, unit, memo}]: what "sense" reads.

   actuators  [{name, args, memo}]: what "actuate" operates.

   params  [{name, type, unit, range, default, mode, memo}]: what
      "get_param" and "set_param" reach.  "mode" is the access in Linux
      permission notation -- 4 read-only, 6 read-write, 2 write-only,
      the x bit unused -- mirroring "read"/"write" of the descriptor
      (Section 9.1.3).

   events  [{name, memo}]: what the peer publishes, under the name that
      appears in the "name" member of the event.

   The "args" member of an entry names the parameters of the procedure
   or of the actuator, in positional order.  A caller MAY use those
   names as the keys of "args"; the entry states no preference between
   the forms, and an entry that names no parameters can only be called
   by position.  A handler decides for itself whether it takes one form,
   the other or a mix of both, and refuses what it does not take in
   RESULT.  "type" names a value type, "unit" the unit of the value,
   "range" the two numbers the value lies between and "default" the
   value used when a call supplies none; all four are OPTIONAL and all
   four are meant for a program.  "memo" is a short text meant for a
   human.  "mode" is the access of the parameter as a number in Linux
   permission notation (r=4, w=2, x unused): 4 read-only, 6 read-write,
   2 write-only.  It is the application-layer signal that tells a caller
   whether "get_param" and "set_param" will be answered or refused
   before it is tried.

9.1.3.  Sensors, Actuators and Parameters

   Besides its procedures, a device offers sensors, actuators and
   parameters, and each is reached through one instruction of Table 20
   rather than by a name of its own.

   *  "sense" reads one sensor.  Its "name" argument names a member of
      the "sensors" array of metadata, and the value returned is the
      reading.  A sensor is read-only: no instruction of this profile
      writes one.

   *  "actuate" operates one actuator.  Its "name" argument names a
      member of the "actuators" array, and the arguments that follow
      are those the actuator declares, bound by name or, after "name",
      by position.  An actuator has no name of its own in this protocol:
      a call that names one directly is unknown.

   *  "get_param" and "set_param" read and write one device parameter.
      "name" names a member of the "params" array and "value" is the
      value written.  A parameter is a setting of the device and not a
      measurement; a measurement is a sensor.  A parameter whose "mode"
      member of metadata is 4 (read-only) MUST refuse "set_param" in
      RESULT; 2 (write-only) refuses "get_param" too.

   A name that is not in the corresponding array is unknown, and an
   actuator that refuses what it was asked to do, like any other failure
   of a call, is answered in RESULT and not with ERROR (Section 6.4.2).


9.2.  Topic Namespaces

9.2.1.  The Registry

   The topics of this document and of the profile of Section 9 are
   listed in Table 21.  The columns are the topic name, the component
   that raises the event and the shape of "data" in the event.  A shape
   is informative: it belongs to the topic, and a consumer MUST ignore a
   member it does not know (Section 11).

   Two kinds of topic appear here.  A PubSub topic travels on the wire:
   the peer publishes it as an EVENT frame and it reaches a session only
   after that session has SUBSCRIBEd to it (Sections 5.5 to 5.7).  A
   pseudo-topic never travels on the PubSub pipeline: the client runtime
   raises it as an event of the same model in response to a protocol
   frame or a local condition, no EVENT carries it and no SUBSCRIBE
   applies to it.  In Table 21 a pseudo-topic has Publisher "runtime" or
   "tunnel"; the "peer" and "any" topics are PubSub topics, except that
   "device.connection" may be either (Section 9.2.1).

   device.connection is dual: when daemon virtualizes the device link it
   is a PubSub topic published by the peer, but when it reports a direct
   device link or the daemon's own connection state it is a pseudo-topic
   raised by the runtime or tunnel.  device.descriptor applies only to
   virtual devices.

   To the application layer the two are indistinguishable: an OctoScript
   script or any client handles a pseudo-topic exactly as it handles a
   PubSub topic -- the same event, the same handler, the same subscribe
   call -- and the split is an implementation detail of how the event
   reaches the client, not of the interface it is handled through.

9.2.2.  Publishers

   The Publisher column names a role and not an implementation.

   *  "peer": the endpoint that owns the device being reported on.

   *  "tunnel": the machinery of Section 6.6, for the tunnel whose name
      appears in the data.  Its topics are pseudo-topics (Section
      9.2.1): raised from tunnel messages, not EVENT.

   *  "runtime": the local client runtime.  Its topics are
      pseudo-topics (Section 9.2.1): they are raised in response to a
      protocol frame or a local condition and never carried by an EVENT
      frame, so no SUBSCRIBE applies to them.

   *  "any": no restriction; the topic is an extension point.

   A publisher MAY republish on a topic what it received from
   elsewhere, exactly as [RFC0006] republishes the reports of a peer
   (Section 6.4); it MUST NOT invent an event for a topic it does not
   own.  A republished event carries the data of the original, and a
   consumer cannot tell the two apart unless the data says so.

9.2.3.  Assignment

   The prefixes "device.", "core.", "blobtun.", "rpc." and "pubsub." are
   reserved, and so is every name listed in Table 21.  A topic whose
   name begins with an underscore is reserved for future standard
   extensions.

   *  A topic filter MAY contain the wildcards "+" and "#" (Section
      6.5.2); a published topic is always a concrete name, and "+" and
      "#" are reserved and MUST NOT appear in one.  "device.+" matches
      only the two-level topics of the device namespace, and "device.#"
      matches those and any deeper topic.

   *  A name under a reserved prefix that is not listed is unassigned.
      A publisher MUST NOT publish it, a subscriber MUST NOT expect it,
      and subscribing to the concrete topic fails; a wildcard filter is
      accepted even when it currently matches no assigned topic.

   *  Names are assigned only by a document of this series.  An
      application MUST NOT use a reserved prefix for a topic of its own,
      and MUST NOT read a meaning into a reserved name that it does not
      find in Table 21.

   *  "x." is reserved for private use.  A topic under it is
      application-defined, is never assigned by this series and MAY be
      used by anyone; two applications that meet on one session agree on
      its meaning between themselves.

   *  A topic whose first label is none of these is application-defined.
      It SHOULD be named after the application that owns it, so that two
      applications cannot collide.

9.2.4.  Using the Topics

   *  An event reports a fact and not a state (Section 10.2): it says
      that something happened.  The present value is asked for with a
      call, and a consumer that has missed events recovers that way; a
      retained message (Section 6.5.3) gives the last value without the
      call.

   *  Delivery is best effort (Section 6.5.3).  A consumer that cannot
      afford to miss an event recovers by asking for the present state
      with a call, which is what the core profile of Section 9.1 is for.

   *  "device.fault" is latched.  A consumer SHOULD hold the fault until
      "device.cleared" arrives for the same name, or until the fault is
      cleared by a call.  A latched fault is not repeated.

   *  "core.metadata" announces that what the responder offers changed.
      A consumer re-reads metadata (Section 6.7) and MUST NOT go on
      using what it cached.

   *  "log.<name>" carries one record of a named facility.  Severity and
      time belong to the data and not to the name, so one subscription
      yields every severity of that facility.

   *  A subscription belongs to one session and is stated again after
      every reconnect (Section 6.5.2).

10.  Service Primitives

   Three primitives are built from the messages of Section 5.  A
   primitive is available only when both endpoints have declared its
   capability (Section 8):

   *  The remote procedure call, capability "rpc", uses CALL
      (Section 5.3) and RESULT (Section 5.4).

   *  Publish/subscribe, capability "pubsub", uses SUBSCRIBE
      (Section 5.6), UNSUBSCRIBE (Section 5.7) and EVENT (Section 5.5).

   *  The blob tunnel, capability "blobtun", uses TUNDATA (Section 5.8)
      and TUNSTAT (Section 5.9).

   Each primitive is symmetric: either endpoint MAY originate it, and
   the roles of initiator and responder established by Section 6 grant
   neither side a privilege in any of them.

10.1.  Remote Procedure Call

   A call asks the peer to execute one named instruction and to report
   the outcome.  The caller sends CALL with an identifier, a procedure
   name and arguments given by name or by position; the receiver answers
   with exactly one RESULT carrying the same identifier.  The procedure,
   and the rules it obeys, are specified in Section 6.4.

   The procedure is specified in Section 6.4 and the members in Sections
   5.3 and 5.4.  What follows is why the primitive has the shape it has,
   and how an application is expected to use it.

   *  The protocol stays out of the procedure.  Names and arguments are
      opaque to it and the set of procedures belongs to the peer, so
      adding one is not a change to this document and needs no new
      version.

   *  Arguments are keyed, so either form can carry them.  A name keeps
      its meaning when a procedure gains a parameter and lets a peer
      reject what it does not define, rather than read a value in the
      wrong position; a position keeps the common case short.

   *  A refusal is an outcome and not an accident.  It travels with the
      answer on purpose: a peer that loses one call still has a session,
      and a proxy can pass a failure on without understanding it.

   *  The answer is self-contained.  Identifier, name and outcome ride
      in the message, so no side table is needed to interpret a reply,
      which is what makes several calls outstanding at once cheap to
      track.

   *  Time is left to the application.  No timeout and no cancellation
      appear here, because only the application knows what a procedure
      does to a machine and how long that may take.

   *  One primitive also carries the incidental traffic.  Heartbeat and
      metadata are ordinary calls (Section 6.7), so they need no
      machinery of their own and appear in the same logs as everything
      else.

   *  An answer that needs several pieces is a stream.  Such an answer
      is carried by a tunnel (Section 6.6) rather than by several
      results, so the shape of a call never changes.

   An application SHOULD:

   *  treat "kind" as the unit of programmatic handling and "message"
      as text meant for a human;

   *  keep both arguments and results small, and move anything large
      into a tunnel, since one frame carries one payload;

   *  decide for itself how long to wait, since no timeout, no retry and
      no cancellation are defined here and a caller that stops waiting
      ignores the RESULT when it arrives (Section 6.4.4);

   *  serialise explicitly when order matters, rather than relying on
      the order in which procedures are executed;

   *  obtain names from metadata and re-read it when the peer announces
      a change.

10.2.  Publish and Subscribe

   A publisher sends EVENT on a topic; a subscriber receives the events
   of the topics it has subscribed to.  There is no broker, the two
   roles meet directly, and either endpoint MAY publish, subscribe or do
   both.  The procedure, and the rules it obeys, are specified in
   Section 6.5.

   The procedure is specified in Section 6.5 and the members in Sections
   5.5 to 5.7.  What follows is why the primitive has the shape it has,
   and how an application is expected to use it.

   *  Asking is answered, publishing is not.  A subscription is a
      request and someone is waiting for it; an event is a notification
      and nobody is.  That asymmetry is what makes an unacknowledged
      push possible without any state to keep in sync.

   *  State lives where it can be rebuilt.  A subscription belongs to a
      session and is stated again after every reconnect, so a publisher
      keeps nothing that can go stale and an idle topic costs nothing.

   *  There is no broker.  The two roles meet directly over the session
      that exchanged HELLO and WELCOME; anything wider is an application
      relaying events, which keeps the primitive small and the trust
      boundary obvious.

   *  A topic is a name, but a subscription is a filter that MAY use the
      wildcards "+" and "#" (Section 6.5.2).  Wildcards are opt-in with
      the "pubsub" capability, so no peer matches a pattern it never
      agreed to, and a publisher delivers only to sessions whose filter
      matches the concrete topic it publishes.

   *  Push is cheap and the pull path carries the same data.  An
      application MAY use either without changing what it receives, so
      the expensive guarantees are paid for only where they are wanted.

   *  An event reports a fact and not a state.  It says that something
      happened; the present value is asked for with a call. Keeping the
      two apart is what lets a consumer recover after a gap.

   An application SHOULD:

   *  subscribe once after a session is established, and again after
      every reconnect;

   *  keep "data" small and self-describing, since its shape belongs to
     the topic and not to this document;

   *  treat a missing event as normal rather than as a failure, and pull
      instead where a gap matters;

   *  not publish faster than the slowest consumer can absorb, since
      this primitive offers no flow control, unlike Section 6.6.

10.3.  The Blob Tunnel

   The blob tunnel carries raw byte streams: firmware images, media
   streams, log uploads and vendor extensions.  Several tunnels MAY
   share one session, distinguished by name.  The procedure, including
   establishment, flow control, retransmission and teardown, is
   specified in Section 6.6.

   The procedure is specified in Section 6.6 and the members in Sections
   5.8 and 5.9.  What follows is why the primitive has the shape it has,
   and how an application is expected to use it.

   *  One mechanism for every byte stream.  Whatever does not fit in one
      frame and does not need the request and answer shape is a tunnel:
      firmware, logs, media, and anything a vendor adds later, so a
      profile gains bulk transfer without new message types.

   *  Nothing is invented twice.  Compression comes from the frame layer
      (Section 3.5), and so does every protection that [RFC0009] adds,
      so a tunnel is protected exactly as every other message is and
      needs no cryptography of its own.

   *  Offsets are what make a stream recoverable.  Because each slice
      says where it belongs, a gap can be filled and a transfer can
      resume after a restart, and the price is one integer that an
      application MAY ignore.

   *  Credit is granted and never inferred.  Flow control is driven by
      the receiver rather than guessed by the sender, which is what
      makes a slow consumer safe; publish/subscribe offers no such
      guarantee (Section 10.2).

   *  A stream keeps to itself.  A tunnel is established, advanced,
      closed and destroyed without ever touching the request numbering,
      so a long transfer cannot disturb the calls around it.

   *  A tunnel is only a name.  Several share one session, so parallel
      transfers need no second connection, and a tunnel error concerns
      one tunnel and never the session.

   An application SHOULD:

   *  open a tunnel for anything larger than a few frames, rather than
      sending it as the argument of a call or the payload of an event;

   *  use one tunnel per stream and let the name say what it carries;

   *  acknowledge promptly, since a stalled acknowledgement stalls the
      sender whether or not the receiver is consuming data;

   *  destroy the tunnel when it is finished, so that its name and its
      buffers can be reused.

11.  Versioning and Extension Rules

   1.  A version mismatch MUST be reported with E_BAD_VERSION.  Minor
       evolution is carried by the capability set and by the rule that
       unknown material is ignored.

   2.  New message types use unused type values.  An implementation that
      receives an unknown type reports E_UNKNOWN_TYPE and continues.

   3.  New flag bits are only added, never redefined; unknown bits MUST
       be ignored.  Session-scope bits are negotiated.  Bits 0x08 and
       above are assigned by the extensions of Section 3.8 and by no
       other document.

   4.  Unknown fields in a message map MUST be ignored.

   5.  A breaking change increments the version octet once the protocol
       has been published.

   6.  Transform algorithms are named freely (Section 3.6).  An endpoint
       that does not recognise a name ignores it in an offer and MUST
       NOT use it.  A new name MUST NOT reuse the meaning of an existing
       one.

   7.  Authentication methods are named freely (Section 6.2): any name
       MAY be agreed, an endpoint that does not implement it rejects the
       attempt, and a new name MUST NOT reuse the meaning of an existing
       one.

   8.  A longer header is added by a document of the series and is
       selected by the value of "header_len" (Section 3.8).  Adding one
       does not change the header defined here, and a receiver that does
       not implement it rejects the session with E_UNSUPPORTED.

   9.  An extension of Section 3.8 is OPTIONAL and is negotiated in
       HELLO and WELCOME.  An endpoint that does not implement one
       ignores the members that carry it and continues with the core.

12. Security Considerations

   *  This document carries cleartext.  A session that uses no extension
      of Section 3.8 is unauthenticated and unencrypted, and is
      appropriate only for a controlled environment.  Nothing here
      detects a change to a frame or hides what a frame says.

   *  An authenticated session is as strong as the method that was used
      (Section 6.2).  A method that returns a proof authenticates the
      responder to the initiator as well; a method that returns none
      does not, and the initiator then relies on the transport for that
      direction.  A method whose credential reveals the secret SHOULD be
      combined with [RFC0009] or with [RFC0010].

   *  A deployment that needs confidentiality, integrity or per-frame
      verification uses one of the two extensions and not both:
      [RFC0009] protects the frames themselves, and [RFC0010] puts the
      session inside a secure transport.  What each costs, and when each
      is appropriate, is discussed there.

   *  Algorithm selection is an intersection of offers.  An endpoint
      that requires a particular algorithm MUST offer only that
      algorithm and MUST close the session when WELCOME confirms
      another.  An offer is not a downgrade path: a peer cannot make an
      endpoint use an algorithm it did not accept.

   *  A receiver MUST NOT interpret as cleartext a frame it has
      rejected, whatever the reason for the rejection.

   *  An endpoint SHOULD bind the loopback address (IPv4 127.0.0.1 or
      IPv6 ::1) unless remote access is intended.

13. IANA Considerations

   This document has no IANA actions.  It requests no name, no number
   and no code point, and it establishes no registry administered by
   IANA.

   The namespaces this document defines are maintained by this series,
   and a value is added to one of them only by a document of the series,
   under the rules of Section 11.  They are:

   *  Message type values (Section 5).

   *  Flag bits (Section 3.2).  Bits 0x08 and above are assigned by the
      documents that define the extensions of Section 3.8.

   *  Header lengths, that is, the values of "header_len"
      (Section 3.8).

   *  Capability names (Section 8).

   *  Error codes; the registry is reproduced in Appendix A.

   *  Reserved topic prefixes (Section 9.2).

   Two namespaces are not maintained at all.  A name in either of them
   is chosen by agreement between the two endpoints of one session,
   carries no meaning beyond that session, and is never registered:

   *  Transform algorithm names (Section 3.6 and [RFC0009]).

   *  Authentication method names (Section 6.2).

   No port number is requested.  The RECOMMENDED port of Section 7.4 is
   a convenience of this document and not an assignment: a deployment
   MAY use it and is equally free to use another.  The URI scheme "ocp"
   is not registered either; it is a convention of this series, and the
   scheme of a secure session is registered nowhere and defined by
   [RFC0010].

   The codes are in five groups, lowest first, and the same order is
   used wherever they are listed:

   *  0x0000 to 0x0003: the session cannot be read at all, because the
      octets are not a frame, the version is not served, or the session
      was not opened.

   *  0x0004 to 0x0006: one frame and the value it carries.

   *  0x0007 to 0x000B: a peer refuses what was asked of it, because the
      session has ended, the feature is not supported, the peer is
      limiting or busy, or the caller is not authorised.

   *  0x000C and 0x000D: a tunnel.

   *  0x000E: a transform.

   The same registry is used by the "error" member of tunnel state
   frames.  A stream parser that simply needs more octets is not a
   protocol error and MUST NOT be reported as one.

   These are all the codes of this document, and 0x000E is the last of
   them.  A document of the series that needs more adds them after it,
   so the core never grows into the range of an extension and an
   extension never takes a code the core already owns: [RFC0009] starts
   at 0x000F.  Once a code has been published it is never renumbered and
   its number is never reused.

Appendix B.  Test Vectors

B.1.  Minimal session

   No authentication, no compression and no extension of Section 3.8.
   The header of the first frame, octet by octet: 4F 43 50 are the magic
   octets, 01 the version, 01 the type HELLO, 00 no flags, 00 10 the
   header length of sixteen octets, 00 00 00 00 the first sequence
   number and 00 00 00 1F a payload of thirty-one octets.

      C to S  HELLO   {"proto":1, "client":"octo-test", "caps":["rpc",
                       "pubsub"],
                       "max_payload":1048576,"flags":0}
              header: 4F 43 50 01 01 00 00 10 00 00 00 00 00 00 00 1F
      S to C  WELCOME {"proto":1,"session":"s1","server":"octod-test",
                       "caps":["rpc", "blobtun"],
                       "max_payload":1048576, "flags":0}
      C to S  CALL    {"id":1,"name":"metadata","args":{}}
      S to C  RESULT  {"id":1,"ok":true,"value":[]}

B.2.  Compression

   With a compression algorithm agreed, the octets of a frame carrying
   4096 zero octets are smaller with F_COMP set than without it, and
   decoding with F_COMP set reproduces the original value.

B.3.  Tunnel Establishment

   A request with open set to an empty map is answered with open set to
   {"ok": true}, an acknowledgement and a window; a subsequent TUNDATA
   with a known offset is acknowledged by an advance of "ack".

B.4.  Algorithm Negotiation

   A HELLO whose "algs" member names only algorithms the responder does
   not implement is answered with a WELCOME in which the corresponding
   key is absent and the corresponding session flag is cleared; a HELLO
   that names one the responder implements is answered with that name.

   The vectors for the primitives of [RFC0009] are in that document.
