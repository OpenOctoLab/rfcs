                     The OctoScript Package Manager

Abstract

   This document specifies the package manager of OctoScript
   [RFC0003]: how a package is named, how a version is written, how an
   import path of the form @<publisher>/<package>:<version> resolves
   to one, and what a host does to fetch, build and install it.  A
   package is a unit of distribution, not a unit of the language: the
   language sees only the module an import binds.

   Section 4 is written.  The rest of this document is a skeleton: its
   scope and its section names are fixed so that [RFC0003] and
   [RFC0012] can refer to them; the substance of each is to be
   written.

1.  Introduction

   Tentacle is the package manager of OctoScript.  It has no binary of
   its own: it is reached through the unified entry, octo, as the
   top-level verbs "octo grab" (install dependencies) and "octo drop"
   (remove them) together with the rest of the lifecycle verbs, or
   behind the "tentacle" namespace, as "octo tentacle grab"; the two
   forms are the same commands.  This section will say what a package
   is, what it carries, and how it differs from the file modules and
   the host units that [RFC0003], Section 10.3 already reaches.

4.  Versions

   A package is asked for by the version identifier written after the
   colon of its import path: @<publisher>/<package>:<version>.  An
   identifier is one of three kinds -- a standard version, a wildcard
   and a pointer -- and which it is decides whether it can move.

   A standard version is written in the dotted notation of SemVer
   [SEMVER]: three non-negative integers separated by dots, with the
   pre-release and build parts of that notation where the package
   wants them.  A standard version is immutable: what it names is
   fixed when the package is published, and a registry MUST NOT move
   it afterwards.  An import that names one therefore always resolves
   to the same content, and two programs that name the same one agree.

   A wildcard is a pattern written in the dotted SemVer notation.  It
   follows the same grammar as a standard version, but a component may
   be a wildcard and the notation may carry a range operator; the
   resolver matches it against the immutable standard versions and
   chooses the highest that satisfies it.  A wildcard may take any of
   the forms below.

   *  A component written *, x or X, or omitted from the right, is a
      wildcard component: 1, 1.2, 1.*.*, 1.x and 1.2.X each match every
      version that agrees to the left.

   *  A caret, ^<version>, allows changes that do not alter the left-
      most non-zero component: ^1.2.3 means >=1.2.3 <2.0.0, ^0.2.3 means
      >=0.2.3 <0.3.0, ^0.0.3 means exactly 0.0.3.

   *  A tilde, ~<version>, allows the right-most named component to
      change: ~1.2.3 means >=1.2.3 <1.3.0, ~1 means >=1.0.0 <2.0.0.

   *  A hyphen range, <a> - <b>, matches versions from a through b
      inclusive; an end of * is open (a - * means at or above a).

   *  A comparison, > >= < <= or =, before a version restricts the
      match to one side of it; several forms may be joined by ||,
      which matches any of them.

   A pre-release in the wildcard limits the match to pre-release
   versions at or above that mark; without one, a wildcard matches
   only releases.  A wildcard that matches no version resolves to
   nothing, and importing it is an error.

   A pointer is any other identifier -- an identifier of [RFC0003],
   Section 2.4, chosen by the publisher.  A pointer stands for one of
   the versions of the package and MAY be moved to another at any
   time, so an import that names one resolves to whatever it stands
   for when the import is resolved, and two resolutions of the same
   pointer MAY disagree.  Three pointers are conventional:

   *  latest -- the version the publisher recommends.

   *  nightly -- the newest build, made and published on the schedule
      the publisher keeps.

   *  lts -- the oldest version the publisher still supports.

   A publisher MAY define further pointers of its own and MAY leave
   any of the three above undefined, so a pointer is nothing but an
   agreement between a publisher and whoever writes the import.  One
   that stands for no version resolves to nothing, and importing it is
   an error.

   The version MAY be left out of an import path, and the path then
   asks for latest.
