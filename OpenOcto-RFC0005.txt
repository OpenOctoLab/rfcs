                 The OpenOcto Device Descriptor Format

Abstract

   A device endpoint of the Octopus Control Protocol [RFC0004] holds no
   knowledge of the machine it serves; everything it knows comes from a
   descriptor.  A descriptor is a TOML document that names the buses,
   states how a procedure call becomes octets on a bus and how received
   octets become named values again, declares what the device
   publishes, and states the sessions it will and will not accept.  It
   carries no control logic: a descriptor translates, and what decides
   what is to be done about what a device reports is a program and not
   a file.  This document specifies that format completely: every
   table, every key, its type and its default, the rules that tie the
   tables to one another, the validation a descriptor undergoes before
   any of it is applied, and the diagnostics a violation produces.

1.  Introduction

   A device endpoint of [RFC0004] knows nothing about the machine it
   serves.  The protocol names no motor, no joint, no sensor and no bus,
   and what a peer offers is discovered rather than assumed.  A
   descriptor supplies that knowledge.  It is data and not code: it is
   read once at start-up, validated as a whole, and then drives the
   endpoint for as long as it runs, so that changing what a device does
   means changing a file and not a program.

   Five ideas shape the format.

   Transport is separate from signalling.  A bus either carries frames
   that this descriptor encodes and decodes, or it is a remote peer
   reached over a session of [RFC0004], and then the peer owns the
   octets.  No other table of the format is affected by which of the two
   it is.

   A remote bus is the recommended one.  A descriptor SHOULD reach a
   device over OCP: the device, or the program that stands in front of
   it, speaks [RFC0004], owns its own octets and is discovered rather
   than described.  A local bus, whose octets this descriptor encodes
   and decodes, is the compatibility path: it is there for a device
   that cannot speak the protocol, whether because it predates it,
   because it will never be updated, or because it is a bus and not a
   computer.  Everything this document says about codecs, parameters
   and signals is about that path and about nothing else.

   One codec serves both directions.  A codec is an ordered list of
   fields, each with a name, a position and a type.  Encoding renders
   arguments into octets; decoding reads octets back into the same
   names.  The two are one list read in opposite directions, so a frame
   template and a frame filter are the same object and cannot disagree
   about what a frame means.

   An instruction is only a procedure.  There is no separate notion of
   an actuator, a sensor or a command: each is a procedure with typed
   arguments, and what distinguishes them is the name a program calls
   and what the procedure does to the machine.

   A descriptor translates and does not control.  It holds no
   reaction, no policy and no program: it says what an instruction
   means on a bus and what a frame means to a program, and nothing in
   it decides what is to be done about what the device reports.  That
   decision belongs to a program on the far side of a session, and
   writing it is not the business of this format.  A descriptor is
   therefore not a place to put behaviour: it is a translation table,
   and the only thing in it that acts is a caller, from outside,
   through an instruction.

   What a descriptor declares reaches a peer through the mechanisms
   [RFC0004] already defines: its instructions appear in discovery
   (Section 14), what it observes is published on the topics of
   Section 14.3, and an instruction on a remote bus is a call on a
   session.  What it declares about a session, including what it
   requires before it will serve one, is Section 6 and is governed by
   [RFC0009] and [RFC0010].

   A descriptor is read by the device daemon of [RFC0006] and by
   nothing else: it is the daemon's translation table and not a
   description that a peer consumes or a device carries.  A program
   written in the language of the series [RFC0003] calls what a
   descriptor declares by the names declared here, and a device that is
   reached directly, with no daemon in front of it, is not described by
   one at all.  Such a device has to speak [RFC0004] itself, which is
   to say that whoever puts it on the network implements an
   OCP-speaking control program on its behalf; the program that calls
   it then needs no descriptor, because the device answers for itself.
   The architecture that puts the daemon, the programs and the protocol
   together is [RFC0002], and a term that this document takes from it
   carries the meaning that document gives it.

   This document replaces an earlier revision of the same name.  A
   descriptor of that revision is rejected and is not migrated: no
   table, no key and no value of it is recognised here, and in
   particular the table [device] is not a bus.

2.  Conventions

   The key words of [IETF-RFC2119] and [IETF-RFC8174] apply.  A
   descriptor is a TOML document [TOML].  The type names used in the
   tables of this document are listed in Table 1.

   [RFC0002] and [RFC0003] are normative for this document.  A term
   that [RFC0002] defines carries the same meaning here, and the
   programs of the series, which are the callers a descriptor serves,
   are written in the language of [RFC0003].

   +=========+=========================================================+
   | Type    | Meaning                                                 |
   +=========+=========================================================+
   | integer | A TOML integer.                                         |
   +---------+---------------------------------------------------------+
   | float   | A TOML float; an integer is accepted.                   |
   +---------+---------------------------------------------------------+
   | boolean | A TOML boolean.                                         |
   +---------+---------------------------------------------------------+
   | string  | A TOML string.                                          |
   +---------+---------------------------------------------------------+
   | array   | A TOML array; the element type is stated where used.    |
   +---------+---------------------------------------------------------+
   | table   | A TOML table.                                           |
   +---------+---------------------------------------------------------+
   | value   | An integer, a float or a string.                        |
   +---------+---------------------------------------------------------+
   | any     | Any of the above.                                       |
   +---------+---------------------------------------------------------+

                 Table 1: Type Names Used in This Document

   Names.  Every object of this format has a name: a bus, a codec, an
   instruction, a parameter, a signal, an endpoint, a session, an
   enumeration and a field.  A name is a non-empty string and is
   compared as exact octets.  A name SHOULD consist only of ASCII
   letters, digits and the three characters "_", "-" and "."; a name
   that contains anything else is accepted but is awkward to carry in a
   procedure name or in a topic.  The namespaces are separate, so a bus
   and an instruction MAY share a name and the key that names one says
   which is meant; two objects of the same kind MUST NOT share one.

   Order.  Where a list is declared, as the fields of a codec or the
   arguments of an instruction, the order of declaration is part of its
   meaning (Sections 9.1 and 10).  Everywhere else the order of keys
   carries no meaning, and a descriptor MUST NOT rely on it.

   Paths.  A key path is written as the TOML path of the table or the
   key it names, for example bus.main.transport.  Diagnostics are
   written with it (Section 13).

   Strictness.  A key that a table does not define is an error, in
   every table of this format and not only in some of them.  Nothing is
   accepted and then ignored: a descriptor that no one validates is a
   descriptor that no one can reason about.

3.  Document Structure

   The top-level tables are listed in Table 2.

   +======================+============================================+
   | Table                | Purpose                                    |
   +======================+============================================+
   | [descriptor]         | Identity and format version of this        |
   |                      | document (Section 4).                      |
   +----------------------+--------------------------------------------+
   | [endpoint.<name>]    | One place the endpoint listens or connects |
   |                      | (Section 5).                               |
   +----------------------+--------------------------------------------+
   | [session.<name>]     | What one session offers, requires and is   |
   |                      | carried by (Section 6).                    |
   +----------------------+--------------------------------------------+
   | [bus.<name>]         | One frame carrier, local or remote         |
   |                      | (Section 7).                               |
   +----------------------+--------------------------------------------+
   | [enum.<name>]        | A map from integers to names (Section 8).  |
   +----------------------+--------------------------------------------+
   | [codec.<name>]       | One frame layout (Section 9).              |
   +----------------------+--------------------------------------------+
   | [instruction.<name>] | One procedure a program may call           |
   |                      | (Section 10).                              |
   +----------------------+--------------------------------------------+
   | [param.<name>]       | One named value of the device              |
   |                      | (Section 11).                              |
   +----------------------+--------------------------------------------+
   | [signal.<name>]      | One thing the device reports (Section 12). |
   +----------------------+--------------------------------------------+

                      Table 2: Top-Level Tables

   A descriptor MUST declare at least one bus.  A key that names
   another object MUST name one that is declared; a reference to
   nothing is a load-time error and not a run-time surprise.  Three
   keys, the "bus" of a codec, of an instruction and of a parameter,
   default to the first bus declared; a descriptor SHOULD state the bus
   rather than rely on the order of the tables.

   The descriptor is found by, in decreasing priority:

   1.  an explicit path given to the endpoint;

   2.  the environment variable OCTO_DESCRIPTOR;

   3.  a file named "octo.toml" in the working directory;

   4.  a file of the same name below the user configuration directory;

   5.  a default packaged with the implementation.

   A missing file and a malformed document are both fatal and both name
   the path (Appendix A).  A descriptor is applied as a whole: an
   endpoint MUST NOT start with a part of one.

   A conforming implementation reads a descriptor of format 1, the
   version defined here.  A descriptor whose "format" is a value it does
   not implement MUST be rejected and MUST NOT be guessed at.

   The keys of [descriptor] are listed in Table 3.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | format      | integer        | REQUIRED.  The version of the      |
   |             |                | format; 1 in this document.        |
   +-------------+----------------+------------------------------------+
   | id          | string         | OPTIONAL.  A stable identity of    |
   |             |                | the device.  Reported with the     |
   |             |                | descriptor topic (Section 14.3).   |
   +-------------+----------------+------------------------------------+
   | name        | string         | OPTIONAL.  A name meant for a      |
   |             |                | human.                             |
   +-------------+----------------+------------------------------------+
   | help        | string         | OPTIONAL.  A description of the    |
   |             |                | device, in English, meant for a    |
   |             |                | human.                             |
   +-------------+----------------+------------------------------------+

                   Table 3: Keys of the Descriptor Table

   An implementation MUST NOT infer a device identity from a name: "id"
   is the identity and "name" is a label.

      [descriptor]
      format = 1
      id     = "octo-arm-01"
      name   = "Left arm"
      help   = "Six-axis arm on the port manipulator."

5.  Endpoint Tables

   [endpoint.<name>] declares one place the endpoint listens on or
   connects to.  An endpoint whose "mode" is "listen" is the responder
   of [RFC0004], Section 6; one whose "mode" is "connect" is the
   initiator and sends HELLO.  The keys are listed in Table 4.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | mode        | string         | REQUIRED.  "listen" or "connect".  |
   +-------------+----------------+------------------------------------+
   | host        | string         | The address to bind, for "listen", |
   |             |                | or to reach, for "connect".        |
   |             |                | Default "127.0.0.1" for "listen";  |
   |             |                | REQUIRED for "connect".            |
   +-------------+----------------+------------------------------------+
   | port        | integer        | Default 6286, the port recommended |
   |             |                | by [RFC0004], Section 7.4, or      |
   |             |                | 16286 when the session of this     |
   |             |                | endpoint uses a secure transport   |
   |             |                | [RFC0010].                         |
   +-------------+----------------+------------------------------------+
   | session     | string         | The session this endpoint speaks.  |
   |             |                | Default "default".                 |
   +-------------+----------------+------------------------------------+
   | caps        | array, text    | The capabilities of [RFC0004],     |
   |             |                | Section 8.  Default ["rpc",        |
   |             |                | "pubsub", "blobtun"].              |
   +-------------+----------------+------------------------------------+
   | max_payload | integer        | Largest payload accepted, in       |
   |             |                | octets. Default 1048576.           |
   +-------------+----------------+------------------------------------+
   | window      | integer        | Tunnel receive window, in octets.  |
   |             |                | Default 65536.                     |
   +-------------+----------------+------------------------------------+
   | slice       | integer        | Tunnel slice size, in octets.      |
   |             |                | Default 8192.                      |
   +-------------+----------------+------------------------------------+
   | buffer      | integer        | Bound on received but unconsumed   |
   |             |                | tunnel octets.  Default 262144.    |
   +-------------+----------------+------------------------------------+
   | heartbeat   | float          | Seconds between heartbeat calls; 0 |
   |             |                | disables them.  Default 5.0.       |
   +-------------+----------------+------------------------------------+
   | liveness    | float          | Seconds without an answer before a |
   |             |                | peer is considered lost.  Default  |
   |             |                | 15.0.                              |
   +-------------+----------------+------------------------------------+
   | timeout     | float          | Seconds to wait for a connection,  |
   |             |                | or for WELCOME.  Default 3.0.      |
   +-------------+----------------+------------------------------------+
   | retry       | float          | For "connect": seconds between     |
   |             |                | attempts; 0 gives up after one.    |
   |             |                | Default 5.0.                       |
   +-------------+----------------+------------------------------------+
   | enabled     | boolean        | Default true.  When false the      |
   |             |                | endpoint is declared but not       |
   |             |                | opened.                            |
   +-------------+----------------+------------------------------------+

                     Table 4: Keys of an Endpoint Table

   The numbers of Table 4 are the recommendations of [RFC0004],
   Sections 3.3, 6.6.7 and 6.7, restated as defaults; a deployment MAY
   change any of them and none of them is negotiated by this document.

   Several endpoints MAY be declared.  Two endpoints of the same mode
   MUST NOT share a host and a port.  An endpoint whose mode is
   "connect" and whose session requires more than the peer offers is a
   run-time failure of the session and not an error of the descriptor:
   what the peer answers is not known when a file is read.

6.  Session Tables

   [session.<name>] declares what one session offers, what it requires
   and what carries it.  Every endpoint names one, and so does every
   remote bus through its endpoint.  A session named "default" is
   assumed when a key names a session that is not declared: it offers
   the defaults of Section 6.1, has no authentication, no secure
   transport and no requirement.

6.1.  Offers

   The keys of Table 5 are offers: what this endpoint is willing to
   use.  Each is an array of algorithm names, most preferred first, as
   [RFC0004], Section 3.6, requires of an offer.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | comp        | array, text    | Compression algorithms.  Default   |
   |             |                | ["zstd"], which is the default of  |
   |             |                | [RFC0004], Section 3.6.  An empty  |
   |             |                | array offers none.                 |
   +-------------+----------------+------------------------------------+
   | enc         | array, text    | Encryption algorithms of           |
   |             |                | [RFC0009]. Default empty:          |
   |             |                | encryption is not offered.         |
   +-------------+----------------+------------------------------------+
   | itg         | array, text    | Integrity algorithms of [RFC0009]. |
   |             |                | Default empty.                     |
   +-------------+----------------+------------------------------------+
   | ztr         | array, text    | Zero-trust algorithms of           |
   |             |                | [RFC0009]. Default empty.          |
   +-------------+----------------+------------------------------------+
   | hdr         | array, text    | Header forms of [RFC0009], Section |
   |             |                | 3.3: "ext", and "core" for the     |
   |             |                | form of [RFC0004].  Default empty, |
   |             |                | which is the core form.            |
   +-------------+----------------+------------------------------------+

                      Table 5: Keys of an Offer

   The rules of the exchange are those of [RFC0004], Section 6.1, and
   of [RFC0009], Section 9.  Three of them are restated here because a
   descriptor is where they are decided.

   *  A primitive is never switched on by silence.  An absent or empty
      "enc", "itg", "ztr" or "hdr" offers nothing, unlike "comp", whose
      absence offers the default algorithm.

   *  "hdr" MUST contain "ext" when "enc", "itg" or "ztr" is not empty,
      and MUST be empty when all three are: the two fields the longer
      header adds exist only to feed a primitive.  A session that
      offers one without the other is an error of the descriptor.

   *  A session that offers "enc" or "ztr" MUST declare authentication
      with a secret (Section 6.2), or a method that yields one, because
      a primitive that has no key produces a session that fails on its
      first protected frame.

   The names are compared as exact strings and are not registered; a
   name an endpoint does not implement MUST be ignored in an offer and
   MUST NOT be confirmed, as [RFC0004], Section 3.6, requires.

6.2.  Authentication

   The [session.<name>.auth] table is OPTIONAL.  Its keys are listed in
   Table 6; every other key of the table is defined by the method and is
   opaque to this document, exactly as the "auth" member of HELLO is
   opaque to [RFC0004], Section 6.2.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | method      | string         | REQUIRED.  The authentication      |
   |             |                | method, named as [RFC0004],        |
   |             |                | Section 6.2, names one.  Compared  |
   |             |                | exactly.                           |
   +-------------+----------------+------------------------------------+
   | secret      | string         | OPTIONAL.  The secret, written in  |
   |             |                | the descriptor.  Discouraged       |
   |             |                | (Section 15).                      |
   +-------------+----------------+------------------------------------+
   | secret_env  | string         | OPTIONAL.  The name of an          |
   |             |                | environment variable that holds    |
   |             |                | the secret.                        |
   +-------------+----------------+------------------------------------+

                 Table 6: Keys of the Authentication Table

   At most one of "secret" and "secret_env" MAY be given.  A method
   that needs no secret is given neither.  When a session is
   authenticated, the keys of [RFC0009] are derived from the secret the
   method yields or from this one, as [RFC0009], Section 7.1, states.

   The choice of method belongs to the initiator and is not negotiated.
   A descriptor therefore states what this endpoint accepts when it is
   the responder and what it offers when it is the initiator; a method
   this implementation does not implement is an error of the
   descriptor.

6.3.  Secure Transport

   The [session.<name>.transport] table is OPTIONAL and selects the
   binding of [RFC0010].  The keys are listed in Table 7.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | kind        | string         | "none", "tls", "dtls" or "quic".   |
   |             |                | Default "none": the session is     |
   |             |                | carried by the transport of        |
   |             |                | [RFC0004].                         |
   +-------------+----------------+------------------------------------+
   | alpn        | string         | The ALPN identifier of [RFC0010],  |
   |             |                | Section 4.2.  Default "ocp/1".     |
   +-------------+----------------+------------------------------------+
   | ca          | string         | OPTIONAL.  Path to the trust       |
   |             |                | anchors the peer is validated      |
   |             |                | against.                           |
   +-------------+----------------+------------------------------------+
   | pin         | string         | OPTIONAL.  The pin of the peer:    |
   |             |                | "sha256:" followed by the hex      |
   |             |                | digits of the hash of its public   |
   |             |                | key or of its certificate.         |
   +-------------+----------------+------------------------------------+
   | cert        | string         | OPTIONAL.  Path to the certificate |
   |             |                | this endpoint presents as a        |
   |             |                | client.                            |
   +-------------+----------------+------------------------------------+
   | key         | string         | OPTIONAL.  Path to the private key |
   |             |                | of "cert".                         |
   +-------------+----------------+------------------------------------+
   | sni         | string         | OPTIONAL.  The name sent in the    |
   |             |                | Server Name Indication.  Default   |
   |             |                | "host".                            |
   +-------------+----------------+------------------------------------+
   | min_version | string         | The lowest version of the          |
   |             |                | transport that is accepted: "1.2"  |
   |             |                | or "1.3". Default "1.2".           |
   +-------------+----------------+------------------------------------+

                  Table 7: Keys of the Transport Table

   The peer is always validated, as [RFC0010], Section 4.4, requires;
   this document defines no key that turns validation off.  A value of
   "min_version" below "1.2" MUST be rejected, and so must a value that
   names a version this implementation does not implement.

   A session that uses a secure transport does not use [RFC0009]:
   "enc", "itg", "ztr" and "hdr" MUST be empty when "kind" is not
   "none", and a descriptor that offers both is an error.  The two are
   alternatives, as [RFC0010], Section 1.1, states, and a descriptor
   that asks for both has not answered the question of which one
   protects the session.

6.4.  Requirements

   The [session.<name>.require] table is OPTIONAL.  Its keys are listed
   in Table 8; each is a boolean and each is false by default.  A
   requirement says what a session that does not meet it does.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | auth        | boolean        | Refuse a session that is not       |
   |             |                | authenticated.                     |
   +-------------+----------------+------------------------------------+
   | comp        | boolean        | Refuse a session on which no       |
   |             |                | compression algorithm was agreed.  |
   +-------------+----------------+------------------------------------+
   | enc         | boolean        | Refuse a session on which          |
   |             |                | encryption was not agreed.         |
   +-------------+----------------+------------------------------------+
   | itg         | boolean        | Refuse a session on which no       |
   |             |                | integrity algorithm was agreed.    |
   +-------------+----------------+------------------------------------+
   | ztr         | boolean        | Refuse a session on which no zero- |
   |             |                | trust algorithm was agreed.        |
   +-------------+----------------+------------------------------------+

                 Table 8: Keys of the Requirement Table

   A session that does not meet a requirement is refused, and is
   refused rather than served without what was required: an
   unauthenticated session is worse than no session.  As [RFC0009],
   Section 11, states, an endpoint that is configured to require a
   primitive and cannot negotiate it closes the session instead of
   serving it in cleartext.

   A requirement MUST be satisfiable by what the same session offers:
   requiring a primitive that is not offered, requiring "auth" without
   an "auth" table, or requiring "enc" or "ztr" without a secret, is an
   error of the descriptor.

7.  Bus Tables

   [bus.<name>] declares one frame carrier.  A bus is local when it
   names a "transport" and remote when it names an "endpoint": a remote
   bus is a peer reached over a session, and the octets belong to that
   peer.  The recommended kind is the remote one, and the local kind
   exists for a device that cannot be reached over the protocol
   (below).  The keys are listed in Table 9.

   +=============+================+====================================+
   | Key         | Type           | Meaning                            |
   +=============+================+====================================+
   | transport   | string         | The name of a bus transport.       |
   |             |                | REQUIRED for a local bus; MUST NOT |
   |             |                | be given for a remote one.         |
   +-------------+----------------+------------------------------------+
   | endpoint    | string         | The name of an endpoint whose mode |
   |             |                | is "connect".  REQUIRED for a      |
   |             |                | remote bus; MUST NOT be given for  |
   |             |                | a local one.                       |
   +-------------+----------------+------------------------------------+
   | mtu         | integer        | The largest number of data octets  |
   |             |                | one frame carries.  Default 8.     |
   +-------------+----------------+------------------------------------+
   | timeout     | float          | Seconds to wait for a frame that   |
   |             |                | answers one that was sent. Default |
   |             |                | 3.0.                               |
   +-------------+----------------+------------------------------------+
   | enabled     | boolean        | Default true.  When false the bus  |
   |             |                | is declared but not opened.        |
   +-------------+----------------+------------------------------------+

                       Table 9: Keys of a Bus Table

   The [bus.<name>.options] table is OPTIONAL.  Its keys are defined by
   the transport named by "transport" and are passed to it unchanged,
   so that a transport gains settings without a change to this
   document; a transport that is given a key it does not define rejects
   the descriptor.  A remote bus MUST NOT declare it.

   The name of a bus is the name a program passes in the "bus" member
   of a bus write ([RFC0004], Section 9.2) and the name that appears in
   the events of Section 14.3.

   The transport name "loopback" MUST be implemented by every
   conforming implementation.  It retains every frame that is sent so
   that it can be received again, touches no hardware, and is the means
   of exercising a descriptor without a device.  Every other name is
   implementation-defined and is discoverable from the command line
   [RFC0007]; a name this implementation does not implement is an error
   of the descriptor.

   A local bus is one whose octets this descriptor describes; a remote
   bus is one whose octets a peer describes.  No codec, no parameter and
   no local instruction MAY be declared for a remote bus (Sections 9,
   10 and 11), and an instruction on a remote bus is a call forwarded
   to the peer.

   Which of the two a descriptor uses is not a matter of taste, and a
   descriptor SHOULD use a remote bus.  [RFC0004] already carries
   calls, events and byte streams, and a peer that speaks it is
   discovered rather than described: no file has to say what its octets
   mean, and the device answers for itself.  A local bus is the
   compatibility path, taken when a device cannot speak the protocol:
   hardware that predates it, a machine that will never be updated, a
   bus that is a bus and not a computer.  Everything in Sections 9 to
   12 exists for that path and for nothing else.

   A device that is called directly, with no daemon in front of it, is
   not described here at all.  Such a device speaks [RFC0004] itself,
   which is to say that whoever puts it on the network implements an
   OCP-speaking control program on its behalf; the program that calls
   it then needs no descriptor, because there is nothing left to
   translate.

   A field carries a value of one of three kinds, and which one is
   decided by its type and by its "scale" and "bias".  A field of an
   integer type whose "scale" and "bias" are their defaults carries an
   integer of that type.  Every other numeric field carries a float: a
   float field carries one, and so does an integer field that is scaled
   or biased, because what a program sees is the physical value and not
   the raw one.  A field of type "bytes" carries a byte string.  This is
   the value type of the field, and it is what the type of an argument
   (Section 10) and the type of a parameter (Section 11) are checked
   against.

   The layout rules are:

   *  A field MUST NOT begin before zero and MUST NOT extend past the
      "mtu" of its bus.  A field that does is an error of the
      descriptor, and so is a "len" larger than the "mtu".

   *  Two fields MUST NOT share an octet.  A gap is allowed and the
      octets of a gap are zero when encoding and ignored when decoding.

   *  A field of type "bytes" whose "const" is given MUST have "count"
      equal to the number of octets the literal writes.

      [codec.drive]
      bus  = "main"
      addr = 0x123
      len  = 8

      [[codec.drive.field]]
      name  = "cmd"
      type  = "u8"
      const = 0xA1

      [[codec.drive.field]]
      name  = "speed"
      type  = "i16"
      scale = 0.01
      unit  = "rad/s"
      range = [-31.0, 31.0]

      [[codec.drive.field]]
      name    = "mode"
      type    = "u8"
      enum    = "mode"
      default = 1

   The codec above is eight data octets wide: one for "cmd", two for
   "speed" and one for "mode", with four octets of gap that are written
   as zero because "len" is 8.  A caller that names no "mode" gets 1,
   which the enumeration calls "run".

9.2.  Encoding

   Encoding renders a codec and a set of bound values into the data
   octets of a frame.  A value is bound to a field by its name: by an
   argument of an instruction (Section 10), by the value a parameter is
   written with (Section 11) or by the "default" of the field.  Every
   field that has a name MUST be bound, and a binding that names no
   field is an error of the descriptor.

   For each field, in order:

   1.  The physical value is taken from the binding, or from "default"
       when the binding supplies none.  A field with a name that is
       neither bound nor has a "default" is an error of the descriptor.

   2.  When "enum" is given and the value is a string, the value is the
       integer the enumeration maps it to.  A string the enumeration
       does not name is an error of the call.

   3.  When "range" is given, the physical value MUST lie within it.  A
       value that does not is an error of the call, unless "saturate" is
       true, in which case the value is clamped to the nearer end.

   4.  The raw value is the physical value minus "bias", divided by
       "scale", rounded to the nearest integer for an integer type.  A
       raw value that does not fit the width of the type is an error of
       the call.

   5.  The raw value is written at "at" in the order named by "endian".
       A "const" field is written from its literal and takes no
       binding.  The octets of a gap and the octets past the last field
       up to "len" are zero.

   Constant fields are what make a codec a template rather than a
   record: they are the parts of a frame that a caller never chooses.

9.3.  Decoding and Matching

   A frame that a bus receives is offered to the codecs of that bus, in
   the order they are declared.  A codec matches when all of the
   following hold:

   1.  The address of the frame equals "addr".

   2.  The data is at least as long as the width of the codec, and,
       when "len" is declared, exactly as long.

   3.  Every field with a "const" is equal to its literal.

   The first codec that matches decodes the frame and no other codec is
   tried.  For each field, in order, the raw value is read at "at" in
   the order named by "endian"; the physical value is the raw value
   multiplied by "scale" plus "bias"; when "enum" is given and the
   enumeration names the result, the value is that name.  A value is
   reported under the name of its field, and the octets of a gap are
   discarded.

   Decoding applies no "range": a range is a guard on what this
   endpoint sends and not a filter on what a device reports, and a
   device that reports a value outside one is still understood.

   A frame that matches no codec is not discarded silently.  It is
   published on the topic "bus.rx" with its bus, its address and its
   octets (Section 14.3), so that no traffic that a bus carried is
   invisible to a program.

   The name of an instruction is the name a program passes in the "name"
   member of CALL ([RFC0004], Section 5.3).  It MUST NOT be one of the
   reserved names of Section 14.1.

   On a local bus the instruction renders "req" with the arguments of
   the call and writes it to the bus.  The rules of binding are those of
   Section 9.2, with three additions:

   *  Every argument MUST bind to a field of "req" by name, and every
      named field of "req" MUST be bound by an argument, by its
      "default" or by "const".  A mismatch is an error of the
      descriptor, which is what makes discovery truthful.

   *  The type of an argument MUST be the value type of the field it
      binds to (Section 9.1).

   *  When "res" is given, the call does not complete until a frame
      matching that codec arrives on the same bus, and returns the
      values of that codec.  When it is not given, the call completes
      when the frame has been written and returns null.  A call that
      waits and is not answered within "timeout" fails.

   On a remote bus the instruction is forwarded: the call is sent as a
   CALL of [RFC0004] with the same name and with its arguments under
   their names, and the value of the RESULT is returned.  An instruction
   on a remote bus is therefore a declaration that a peer offers
   something, and the descriptor says nothing about its octets.

   A failure of an instruction is an application failure and is
   answered in RESULT, as [RFC0004], Section 6.4.2, requires: an
   argument that does not fit, a value outside a range, a bus that
   cannot be written to and a reply that never arrived are all failures
   of one call and leave the session usable.

      [instruction.drive]
      bus  = "main"
      req  = "drive"
      help = "Spin the joint at a speed."

      [[instruction.drive.arg]]
      name = "speed"
      type = "f32"
      unit = "rad/s"
      range = [-31.0, 31.0]

      [instruction.grip]
      bus  = "remote"
      help = "Close the gripper of the peer."

      [[instruction.grip.arg]]
      name = "force"
      type = "u8"

   names, and the value type of that field (Section 9.1) MUST be the
   type of the parameter.  Every other field of "req" is bound as in
   Section 9.2, from its "default" or from its "const".

   A read sends "req" and answers with the value the endpoint holds.  It
   does not block unless "block" is true, so a program that polls
   neither waits for the bus nor holds up the session; the value is
   replaced whenever a frame matching "res" arrives, whether the frame
   was asked for or not.  A write sends "req" with the value bound to
   "field" and sets the value the endpoint holds to what was written;
   when "res" is given it waits for the answer and fails on timeout.

   most recent value this endpoint has seen, and a program that needs a
   fresh one asks for it with "block" set to true.

   A program reaches a parameter through the instructions of
   Section 14.2.  Whenever the value changes, the endpoint publishes it
   (Section 14.3).

   | codec       | string         | REQUIRED.  The codec that decodes  |

   +-------------+----------------+------------------------------------+
   | clears      | string         | OPTIONAL.  The name of another     |
   |             |                | signal: when this one is reported, |

   |             |                | The named signal MUST have "fault" |
   |             |                | set to true.                       |
   +-------------+----------------+------------------------------------+
   | edge        | boolean        | Default true.  When true, a frame  |

   A frame is decoded once, by the first codec that matches it
   (Section 9.3).  When a signal names that codec, the values are
   published under the name of the signal (Section 14.3); when several
   signals name it, they are published once per signal, because one
   frame may mean two things at once.

   A fault is latched.  Once one is published it is not published again
   until it is cleared, and it is cleared either by a call of
   "device.clear_fault" or by the signal named by "clears"; when it is
   cleared, the endpoint publishes the fact.  A consumer SHOULD hold a
   fault until it sees it cleared, as [RFC0004], Section 9.3.4,
   requires.

   "edge" is what keeps a status frame that a device sends a hundred
   times a second from becoming a hundred events a second: only a change
   is reported.  A consumer that wants the present value asks for it
   with a call instead.

13.  Validation

   A descriptor is validated before any of it is applied, in the
   following order.  A later phase is not begun while an earlier one has
   findings that make it meaningless.

   1.  Read and parse.  The file must exist, be readable and be valid
       TOML, and its "format" must be one this implementation reads.

   2.  Structure.  Every key is one the table defines; every value is of
       the type the table states; every required key is present; every
       name is a valid name; no two objects of one kind share a name.

   3.  References.  Every name that a key names is declared and is of
       the kind the key wants: a bus names a transport or an endpoint, a
       codec names a local bus, an instruction names a codec, a signal
       names a codec, a field names an enumeration.

   4.  Meaning.  The rules of the tables themselves: a field fits the
       "mtu" and shares no octet; an argument binds to a field of its
       own value type (Section 9.1); a parameter names a field of the
       codec it names; a session offers what it requires and does not
       offer [RFC0009] together with [RFC0010].

   5.  Compile.  Every codec is compiled: the offsets are resolved, the
       widths are fixed and the defaults are checked against their
       types.

   An implementation SHOULD report every finding and not only the first,
   because a descriptor is written by a human who would rather fix six
   things at once.  An implementation MUST NOT start with a descriptor
   that has a finding and MUST NOT apply a part of one: a half-applied
   descriptor is a device whose behaviour nobody has written down.

   A diagnostic is written as

      <file>: <path>: <message>

   where <file> is the path of the descriptor, <path> is the key path of
   the table or key that is at fault and <message> is one of Appendix A.
   All of them are in English.

   These are the diagnostics of loading a descriptor, and they are the
   only diagnostics this document defines.  What a running endpoint
   reports, and how a failure of one is classified, belong to the
   taxonomy of [RFC0008]; the tools that read and check a descriptor
   belong to [RFC0007].

14.  Discovery and Publication

14.1.  Reserved Names

   The names of the core profile of [RFC0004], Section 9.1 -- "ping",
   "list_instructions", "device_status" and "poll_events" -- are
   reserved, and so is every name that begins with "bus." or with
   "device.".  A descriptor MUST NOT declare an instruction with a
   reserved name; such a declaration is an error of the descriptor.

14.2.  Standard Instructions

   The instructions of Table 19 are provided by every conforming
   implementation, in addition to the core profile of [RFC0004],
   Section 9.1, and in addition to those a descriptor declares.

   "bus.write" is provided for every bus.  On a local bus it writes the
   octets; on a remote bus it is forwarded to the peer, which is what
   makes a remote bus usable before its peer's descriptor is known.

   A name that a program does not recognise, an argument it does not
   accept and a value that does not fit are answered in RESULT and not
   with ERROR, as [RFC0004], Section 6.4.2, requires.

   an event for a topic it does not own, and a republished event carries
   the data of the original.

15.  Security Considerations

   *  A descriptor is trusted input.  It decides what an instruction
      does to a machine, and it can cause arbitrary frames to be
      written to hardware.  It MUST NOT be accepted from a peer, from a
      session or from anything else that is not the operator, and it
      SHOULD be readable only by the account that runs the endpoint.

   *  A secret in the descriptor is a secret in a file.  "secret_env" is
      preferred over "secret" because an environment variable is not
      copied into a backup, a bug report or a repository.  A secret MUST
      NOT be written to a log, MUST NOT be returned by an instruction
      and MUST NOT appear in a diagnostic.

   *  A requirement is a refusal and not a preference.  An endpoint that
      requires authentication, or a primitive of [RFC0009], closes a
      session that does not meet it rather than serving it without, and
      an implementation MUST NOT offer a way to lower one at run time.

   *  The two protections are alternatives.  A descriptor that offers
      both a secure transport and a primitive of [RFC0009] is rejected
      (Section 6.3), because a session protected twice hides nothing
      extra and leaves two places to make one mistake.

   *  A range is a guard and not an interlock.  It stops a caller from
      asking for a value the field cannot carry; it does not stop a
      machine from being told to move, and it is not a safety function.
      A deployment that needs one puts it where it cannot be turned off
      by editing a file.

   *  An endpoint SHOULD bind the loopback address unless remote access
      is intended, and a remote endpoint SHOULD be authenticated.  A
      session that is not authenticated and is not carried by a secure
      transport is cleartext, as [RFC0004], Section 12, warns.

   *  A remote bus forwards instructions to a peer and applies no
      filtering of its own: what the peer accepts is what it declares,
      and authorisation belongs to the peer.

   *  A descriptor contains no control logic, and that is a property
      worth keeping: nothing in this format acts on what a device
      reports, so the only thing that can move a machine through a
      descriptor is a caller on the other side of a session, which can
      be authenticated, logged and refused.  A deployment that wants a
      device to act on its own writes a program, and puts it where it
      can be reviewed.

16.  IANA Considerations

   This document has no IANA actions.  It requests no name, no number
   and no code point, and it establishes no registry administered by
   IANA.

   The namespaces this document defines are maintained by this series,
   and a value is added to one of them only by a document of the series:

   *  The keys of every table of the format.

   *  The field types of Table 13.

   *  The reserved instruction names of Section 14.1.

   One namespace is not maintained at all.  A bus transport name other
   than "loopback" is chosen by the implementation that provides it,
   carries no meaning beyond that implementation and is never
   registered.

Appendix B.  A Complete Descriptor

   The descriptor below is complete and valid.  Every bus in it is a
   remote one: each is a peer reached over [RFC0004], and the
   descriptor says nothing about the octets those peers use.  What it
   declares is what the daemon serves to its own callers, and how it
   reaches the peers it translates for.

      [descriptor]
      format = 1
      id     = "octo-arm-01"
      name   = "Left arm"
      help   = "Arm controller: two peers, one session each."

      [endpoint.ctl]
      mode    = "listen"
      host    = "127.0.0.1"
      port    = 6286
      session = "ctl"

      [session.ctl]
      comp = ["zstd"]

      [session.ctl.auth]
      method     = "hmac"
      secret_env = "OCTO_ARM_HMAC"

      [session.ctl.require]
      auth = true

      [endpoint.arm]
      mode    = "connect"
      host    = "10.0.0.7"
      port    = 16286
      session = "arm"

      [session.arm.transport]
      kind = "quic"
      pin  = "sha256:9f86d081884c7d659a2feaa0c55ad015"

      [endpoint.gripper]
      mode    = "connect"
      host    = "10.0.0.8"
      port    = 6286
      session = "gripper"

      [session.gripper]
      comp = ["zstd", "deflate"]

      [bus.arm]
      endpoint = "arm"

      [bus.gripper]
      endpoint = "gripper"

      [instruction.drive]
      bus  = "arm"
      help = "Spin a joint at a speed."

      [[instruction.drive.arg]]
      name  = "joint"
      type  = "u8"
      range = [0, 5]

      [[instruction.drive.arg]]
      name  = "speed"
      type  = "f32"
      unit  = "rad/s"
      range = [-31.0, 31.0]

      [instruction.halt]
      bus  = "arm"
      help = "Stop every joint."

      [instruction.grip]
      bus  = "gripper"
      help = "Close the gripper at a force."

      [[instruction.grip.arg]]
      name  = "force"
      type  = "u8"
      range = [0, 100]

   Every instruction above is forwarded: the daemon answers a call by
   sending a CALL of the same name to the peer of its bus, and returns
   what the peer answers.  A program reaches the buses themselves with
   the standard instruction "bus.write" (Section 14.2), which is
   forwarded in the same way.  A descriptor that also drives a device
   which cannot speak the protocol declares a local bus for it, with
   the codecs, parameters and signals that go with it; those are the
   examples of Sections 9.1, 11 and 12, and they are the compatibility
   path rather than this one.
