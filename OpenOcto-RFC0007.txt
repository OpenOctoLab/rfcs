               OpenOcto Command-Line Tools and Interfaces

Abstract

   OctoScript ships as one binary, octo, whose subcommands are its
   verbs: the interpreter ("octo swim", aliases "run" and "exec"), the
   formatter ("octo squeeze", aliases "fmt" and "format"), the checker
   ("octo sift", aliases "lint" and "check"), the interactive session
   ("octo den"), the bytecode utilities, and the package manager
   ("octo grab", "octo drop" and the rest of its verbs).  The daemon
   (octod) and language server (octolsp) are separate products and are
   not entered through octo.  This document specifies each verb's
   interface, the environment it reads, the behaviour of the interactive
   mode, the single endpoint it talks to and the one option that names
   it, and the exact formatting rules.

1.  Introduction

   OctoScript's toolchain is one binary, octo, which dispatches every
   verb it offers.  A verb is a subcommand, and every verb has a primary
   spelling drawn from the octopus world the tools are named for; the
   generic spellings other tools use are bound as visible aliases of the
   same verb, so both reach it and the help shows the mapping.  There
   are no launcher scripts and no per-tool binaries behind it: what this
   document calls "the interpreter" or "the formatter" is a verb of that
   one binary.  The verbs are:

      swim     run programs              (aliases: run, exec)
      squeeze  format source             (aliases: fmt, format)
      sift     check source              (aliases: lint, check)
      den      interactive REPL          (alias: repl)
      ink      dump bytecode as text     (alias: dump)
      stash    write the bytecode cache  (alias: cache)
      wake     load and run a cache      (alias: load)
      unfurl   disassemble a cache       (alias: disasm)
      coil     assemble a text dump      (alias: asm)
      jet      run a text dump           (alias: irload)
      poke     run the tests             (aliases: test, tests)
      grab     install packages          (alias: install)
      drop     remove packages           (alias: remove)
      ... and the rest of the tentacle verbs of [RFC0013].

   "octo poke" feels the water: it compiles a program with its test
   declarations enabled ([RFC0003], Section 7.1.2), runs the top level
   once to set the globals the tests lean on, and then drives each
   lifted `_test_<name>` in the same interpreter.  A test that returns
   passes; one that raises an `Error` fails; one that raises an error
   of kind `Skipped` skipped.  The report names every test and its
   outcome, and the exit status is 1 when anything failed -- the
   Section 11.2 convention of [RFC0003] applied to the driver.

   Every tentacle verb is reached at the top level and, equivalently,
   behind the "tentacle" namespace: "octo grab" and "octo tentacle grab"
   are the same command.  The namespace accepts tentacle verbs only; the
   verbs of this document are not recognized under it.  One further
   verb, "octo", is bound but hidden from the help listing: it prints a
   single line and is an Easter egg, not an interface.  octod (daemon)
   and octolsp (language server) are separate products, not under octo.

   The verbs are specified here as observable interfaces: command-line
   arguments, files read, output produced, exit status, and side
   effects.  All user-facing messages are in English.  Anything a verb
   does not name -- a peer, a transport, a configuration file -- the
   toolchain assumes nothing about: the endpoint is the whole of what it
   knows of the other side.

2.  Conventions

   The key words of [IETF-RFC2119] and [IETF-RFC8174] apply.
   "<command>" means a subcommand of octo, or octod or octolsp.
   Options MAY be written before or after positional arguments.  A path
   that is not absolute is resolved against the working directory.

3.  The Interpreter Command

   The interpreter is the "swim" verb of octo, also spelled "run" and
   "exec".  It starts no REPL: the REPL is "octo den" (Section 4), a
   verb of its own.

      octo swim [options] [script ...]

      Operand / option     Argument      Meaning
      +=====================+==============+=========================+
      | Operand / option    | Argument     | Meaning                 |
      +=====================+==============+=========================+
      | script              | zero or more | Program files to run;   |
      |                     |              | "-" is standard input.  |
      +---------------------+--------------+-------------------------+
      | --endpoint          | address      | Where the peer listens: |
      |                     |              | host:port, or a URI     |
      |                     |              | whose scheme names the  |
      |                     |              | transport.              |
      +---------------------+--------------+-------------------------+
      | --auth-token        | secret       | Token for the session.  |
      +---------------------+--------------+-------------------------+
      | --ca                | path         | Trust anchors for       |
      |                     |              | ocps:// [RFC0010].      |
      +---------------------+--------------+-------------------------+
      | --verbose, -v       | none         | Report progress.        |
      +---------------------+--------------+-------------------------+
      | --color, --no-color | none         | Force or suppress       |
      |                     |              | colour.                 |
      +---------------------+--------------+-------------------------+

   With no script, and with a script named "-", the program is read from
   standard input.  With several program files each file runs in an
   interpreter of its own; the interpreters share one host environment
   and one endpoint.  There is no instance identifier: a program is
   named by the file it came from, that name is what a diagnostic shows,
   and nothing else about it is the toolchain's to invent.

   The interpreter connects to the endpoint only when a program asks for
   it -- through connect() or an unqualified remote call.  It probes
   nothing on start-up and starts nothing itself; what listens at the
   endpoint is the program's business, not the toolchain's.

   Three further options tune the interpreter and change nothing a
   program can observe: --no-warn suppresses the advisory lint pass that
   precedes a run, --locate records per-op source spans so a runtime
   error can show its line, and --jit selects the native backend in a
   binary built with it.

   The exit status is zero on success; non-zero when a program file is
   missing, when lexing, parsing or evaluation fails, and when a usage
   error is detected (Section 5.2 and Appendix B).


4.  The REPL

   The REPL is entered through "octo den" (alias "octo repl"); it is a
   subcommand of octo and is not a fallback of "octo swim": when given no
   program file it is a usage error, not an entry to the REPL.  The REPL reads
   statements from the standard input and requires a terminal; when no
   terminal is attached (for example when the terminal type is "dumb" or
   the input is not a terminal) it refuses to run and exits with
   a non-zero status rather than reading input blindly.

   1.  The prompt is shown; a continuation prompt is shown while a
       statement is incomplete.
   2.  A statement is accumulated until it is complete: an unclosed
       bracket or an unterminated string continues to the next line, as
       does a line that ends with a line-continuation backslash.
   3.  On completion the statement is executed and its value, if any, is
       displayed.
   4.  A failure is reported as an error line and the session continues.
   5.  Input is remembered in a history file in the user's home
       directory.
   6.  The words "exit" and "quit", and an end-of-file, terminate the
       session.

   Interrupting the current line abandons it and leaves the session
   running.

5.  Connection Policy

5.1.  Target Resolution

   The endpoint is resolved from, in decreasing priority: the --endpoint
   option; the OCTO_ENDPOINT environment variable; and the built-in
   default, namely the loopback address and port 6286.  A program MAY
   open further endpoints of its own with connect() ([RFC0003],
   Section 9); those are the language's business, not the toolchain's.

   Nothing here says what listens at the endpoint.  A peer is whatever a
   program connects to; the toolchain neither probes it, starts it, nor
   gives it a name of its own.

5.2.  Usage Errors

   A malformed option argument, an unknown option and an invalid option
   combination are usage errors: they are reported on the error stream
   and the process exits with the usage status.  So is an option that
   cannot apply at all -- --check or -w on standard input, which cannot
   be rewritten.


6.  The Formatter Command

   The formatter is the "squeeze" verb of octo, also spelled "fmt" and
   "format".

      octo squeeze [options] [file ...]

      Option       Meaning
      +=============+==================================================+
      | Option      | Meaning                                          |
      +=============+==================================================+
      | file        | Files to format; "-" or no file means standard   |
      +-------------+--------------------------------------------------+
      | -w, --write | Rewrite files in place and report each one.      |
      +-------------+--------------------------------------------------+
      | --check     | Report files that would change; make no change.  |
      +-------------+--------------------------------------------------+

   Without -w and without --check the formatted text is written to the
   standard output.  With -w every file rewritten is reported.  With
   --check each file that would change is reported and the exit status
   becomes 1.  A file that cannot be read, a source text that cannot be
   lexed and a formatting failure are reported and produce the error
   status; a run reports every such file rather than stopping at the
   first (Appendix C).  The exit status is zero when nothing needed
   changing.  Because the tool reads and writes through the given
   paths, symbolic links are followed and the target file is rewritten.
   -w and --check exclude one another, and neither applies to standard
   input.

7.  The Checker Command

   The checker is the "sift" verb of octo, also spelled "lint" and
   "check".  It reports problems in source text without changing it, and
   exits non-zero when any problem is found.

      octo sift [options] [file ...]

   With no file, or with "-", the standard input is read.  A file that
   cannot be read, a source text that cannot be lexed and a check
   failure are reported and produce the error status; a run reports
   every such file rather than stopping at the first (Appendix C).  The
   exit status is zero when no problem is found.

   The default pass reads the source text alone.  With --strict the
   checker also runs the compiler and reports everything a build would
   refuse -- a field that shadows a core member, an import that resolves
   nowhere -- so a run clean under --strict is what "octo swim" accepts.

8.  Formatting Rules

   Formatting is lossless at the token level: every token's text is
   preserved, including string contents, numeric literal spellings, and
   both comment forms.  Only whitespace, indentation, line breaks inside
   brackets, and brace placement are normalised.

   1.  Indentation is four spaces per brace level.  Only braces increase
       the level; parentheses and brackets do not.
   2.  Each statement occupies its own line.  A line break in the source
       is preserved only outside parentheses and brackets, so an
       expression that spans lines inside brackets is joined onto one
       line.
   3.  Spaces are inserted between operators and their operands, after
       commas, and around colons that introduce a dictionary entry or a
       ternary branch.
   4.  No space is inserted before a closing bracket, a comma, or a
       semicolon, nor after an opening bracket; a unary minus, a logical
       negation and the OPTIONAL-chaining token stay adjacent to their
       operand; the range and spread token stays adjacent to its
       operand, except after a comma.
   5.  An opening parenthesis or bracket after an identifier, a literal,
       a closing bracket or a dot is adjacent to it; otherwise a space
       is inserted.
   6.  A structure header ("if", "elif", "else", "for", "while", "do",
       "loop", "match", "case", "fn", "try", "except", "finally") is on
       the same line as its opening brace.  A closing brace that is
       followed by a continuation keyword shares a line with it, as in
       "} else {".
   7.  An empty block is written inline as "{}".
   8.  A semicolon inside parentheses is kept on the same line;
       elsewhere it becomes a line break.
   9.  Comments are preserved: a comment that was at the end of a line
       stays at the end of that line, separated by two spaces, and a
       comment on its own line stays on its own line at the current
       indentation.  A multi-line block comment is re-emitted line by
       line, keeping its relative indentation.
   10. Blank lines are preserved, with consecutive blank lines collapsed
      into one; blank lines at the beginning of a file are dropped; no
      blank line is introduced inside brackets.
   11. The output ends with exactly one line break.

   Applying the formatter to already formatted text MUST produce
   identical text.

9.  Security Considerations

   *  The interpreter evaluates the program text it is given and MAY
      read its environment.  Only trusted programs SHOULD be run.
   *  A credential given on the command line -- the token --auth-token
      carries -- is visible to other processes on the same host through
      the process table; prefer a channel that does not put it there.
   *  --ca replaces the operating system's trust store for ocps://
      [RFC0010].  A trust anchor broader than the deployment means to
      trust makes every peer signed by it a peer, so the set SHOULD name
      the fleet's own certificates.
   *  Every verb writes files only where it is asked to, and reports the
      path it wrote.

Appendix B.  Exit Statuses

      Status  Meaning
      +========+=======================================================+
      | Status | Meaning                                               |
      +========+=======================================================+
      | 0      | Success.                                              |
      +--------+-------------------------------------------------------+
      | 1      | Program, script or formatting failure; a check that    |
      |        | found a problem; a test run with a failed test; a      |
      |        | file that --check would change.                        |
      +--------+-------------------------------------------------------+
      | 2      | Usage error; an input that cannot be read, or source   |
      |        | text that cannot be lexed or parsed.                   |
      +--------+-------------------------------------------------------+

   Where a run covers several operands, the status is the most severe one
   it reached, so the result does not depend on the order of the
   operands.


Appendix C.  Conformance Notes

   This appendix is non-normative and records differences between this
   document and the reference implementation.

   C.1. The formatter and the checker do not stop at the first failing
   operand: a run reports every file it could not read or could not
   accept and then exits with the most severe status.  Sections 6 and 7
   describe the report, not the stopping rule, so the difference is in
   how many files one run covers.

   C.2. The reference implementation's --strict check runs the same
   compiler a build runs, so it reports an import that resolves nowhere.
   The default pass reads the source text alone and does not.
