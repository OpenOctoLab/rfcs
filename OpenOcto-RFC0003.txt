                     The OctoScript Language

Abstract

   This document specifies OctoScript, a statically typed programming
   language, with types inferred where they are not written, for
   controlling robots and the devices attached to them.  It is designed
   to drive the Octopus Control Protocol [RFC0004] and its
   extensions [RFC0009], [RFC0010] and [RFC0011] from a small surface.
   The language is built around asynchronous remote procedure
   calls and asynchronous events: every call to a device is a future,
   and every event from a device is a message a program waits for.
   To that end the language provides first-class constructs for
   concurrency (spawn), awaiting (await), racing several outcomes
   (race), running statements in parallel (par), and waiting on events,
   topics, channels and time (select, on, wait, sleep).
   It defines the lexical structure, the syntax, the
   value and object model, the concurrency and cancellation model, the
   host interface that binds the language to an OCP session, the
   standard library entry points visible to programs, the meta object of
   an interpreter instance, and the diagnostics a conforming
   implementation produces.

1.  Introduction

   OctoScript is a statically typed, Turing-complete language intended
   for controlling machines over a network.  It combines a compact
   expression syntax with brace-delimited, indentation independent
   blocks, and it is designed to be embedded in a host
   environment that supplies the machine-facing operations by speaking
   OCP [RFC0004] on its behalf.  The value model, the operator set, the
   concurrency model and the library are defined by this document; they
   do not depend on the language in which an implementation is written.

   A program is a sequence of statements executed as a single top-level
   task.  Execution is top-down; the last statement of a program need
   not be terminated.  Statements are separated by newlines or by a
   single semicolon.

   The defining property of the language is that it is asynchronous by
   default at the boundary with hardware.  A call to a device -- sense,
   actuate, get_param, set_param, ping, status or metadata -- is not a
   synchronous function returning a value; it is a request that returns
   a future (Section 3.5).  The future resolves when the device answers
   with a RESULT frame [RFC0004], Section 5.4.  A program reads the
   answer with await (Section 6.2), races several answers with race
   (Section 6.3), or selects among an answer, an event and a timeout
   with select (Section 6.4).  An event from a device -- an EVENT frame
   [RFC0004], Section 5.5 -- is something a program waits for with on
   (Section 6.5) or wait (Section 6.6), never something it polls.

   A conforming implementation MUST support everything specified in this
   document.  Behaviour that is not specified here is unconstrained,
   with one exception: an implementation MUST NOT silently ignore a
   construct it does not support; it MUST reject it during parsing or
   evaluation.

2.  Lexical Structure

2.1.  Input Encoding and Whitespace

   Source text is a sequence of Unicode characters encoded in UTF-8.
   Space, horizontal tab, carriage return and newline are whitespace.
   Indentation carries no meaning: blocks are delimited by braces.

   A newline is a statement separator; it is also significant in two
   other ways that are covered in Section 2.7.

2.2.  Comments

   Two comment forms exist.

   A line comment begins with # and extends to the end of the line.
   A block comment begins with /* and ends with */ and MAY span lines.
   An unterminated block comment is a lexical error.

   Comments are whitespace for the purposes of the grammar.

2.3.  Line Continuation

   A backslash immediately followed by a line break joins the physical
   lines into one logical line.  A backslash followed by anything else
   is a lexical error.

      var x = 1 + \
      2              # x == 3

2.4.  Identifiers and Keywords

   An identifier begins with a letter or an underscore and continues
   with letters, digits and underscores.  Identifiers are case
   sensitive.

   The following words are keywords and MUST NOT be used as identifiers
   or binding targets, and a program MUST NOT use one as a function
   name.  The core standard library is the one exception: it MAY name a
   function after a keyword where the context is unambiguous
   (Section 10.2):

      and      as       async    await    bool     break    case
      chan     char     const    continue default  do       elif
      else     except   f32      f64      false    finally  fn
      for      from     globals  i128     i16      i32      i64
      i8       if       import   in       isize    let      locals
      loop     match    not      null     octo     on       or
      panic    par      pass     race     return   select   sleep
      spawn    str      struct   this     true     try      u128
      u16      u32      u64      u8       usize    until    var
      wait     when     while    within

   Keywords are read-only: using any keyword as an assignment target,
   including compound assignment, is a syntax
   error.  Writing through a member or an index (octo.mock = true) is
   permitted and is not an assignment to the keyword.  octo is the
   reserved global meta object of Section 9.8; it MUST NOT be rebound,
   though its members and indices MAY be written.

   The symbolic forms &&, || and ! are the logical operators; they are
   lexically equivalent to the keywords and, or and not.  The pair != is
   the single operator not equal.
   true and false denote the two boolean values; null denotes the
   absence of a value.

2.5.  Operators and Punctuation

   The operators are:

      Three characters -- compound shift assignment:
         <<=  >>=

      Two characters:
         ==  !=  <=  >=            comparison
         &&  ||                   logical and / or
         +=  -=  *=  /=  &=  |=  ^=           assignment (augmented)
         **  //                   power and floor division
         ..  ?.                   range and optional member
         ->  =>  <-               arrows and channel send/receive
         <<  >>                   shifts

      One character:
         +  -  *  /  %            arithmetic
         &  |  ^  ~               bitwise
         !                         logical not
         =                         assignment
         <  >                     comparison
         ?  :                     conditional

   The characters (, ), {, }, [, ], ,, ; and . are punctuation tokens
   and are not operators.  The token => introduces an arrow function and
   is not the comparison >=.  The token <- is the channel operator:
   as a prefix it receives from a channel, as an infix it sends to one
   (Section 3.6); the infix -> is the same send written value first,
   so v -> ch is the same send as ch <- v.  The token -> also gives a
   function its return type (Section 7.1); context separates the two.

   An at sign (@) is not a valid character; decorator syntax does not
   exist.  There is no identity operator: is is an ordinary identifier
   and comparing with == null is the idiom for emptiness.  There is no
   increment or decrement operator; x += 1 is used instead.

   The longest token wins: >>= is one operator, not >> followed by =.

2.6.  Literals

   A literal denotes a value by its written form.  Numbers, booleans
   and text have literal syntax; containers are written with their own
   bracketed forms (Section 3.2).

   Numeric literals

      An integer literal is a run of decimal digits, optionally
      signed, with an optional 0x/0o/0b base prefix and single
      underscores _ as digit separators between digits.  A
      floating-point literal has a decimal point or an exponent
      (e or E); the exponent is a signed decimal integer.

         let a = 42          # decimal
         let b = 0x2A        # hexadecimal
         let c = 0o17        # octal
         let d = 0b1010      # binary
         let e = 1_000_000   # digit separators
         let f = 3.14        # float
         let g = 1.5e3       # exponent

   Boolean and null literals

      The keywords true and false denote the two boolean values;
      null denotes the absence of a value.

   str literals

      A text value is written between either double or single
      quotes; both quote styles denote the same text kind.  Inside
      a double-quoted string a \" must be escaped and a ' is
      literal, and inside a single-quoted string a ' must be
      escaped and a \" is literal.  The recognised escapes are
      \" \\ \' \n \t \r \0 \xHH and \u{HHHH}.  A single character is
      a one-element str value; there is no separate char kind, and
      the char annotation names it.  An ordinary string never
      interpolates; ${ } in one is literal text.

         let s1 = "actuator"
         let s2 = 'actuator'
         let s3 = "it's ${name}"     # ${ } is inert here
         let s4 = 'say "hi"'         # " is literal in '...' strings

   Template strings

      A template string is written between backticks `...`, may span
      lines, and is the only literal form that interpolates.  A newline
      in the source is kept as a newline, and \` is the only required
      escape.  A template embeds expressions between ${ and }; each is
      evaluated in the enclosing scope and converted to text by the
      formatting rules of Section 10.4.  The expression in the marker
      is loose: any single-line expression that contains no meaningful
      braces may stand there -- a bare name, a member or index chain, a
      call, an arithmetic expression.  A format spec (Section 10.4)
      follows a colon, but only on a bare variable or on a
      parenthesised expression.

         let s = `actuator ${name} = ${speed}`
         let t = `sum ${a + b} of ${items.len()}`
         let doc = `servo ${id}: limit ${max}`
         let lines = `one
                      two with ${id}`

2.7.  Newline Sensitivity

   A newline ends a statement unless one of the following holds: the
   line ends inside a brace, bracket or parenthesis group; the line
   ends inside a template string, which may span lines (Section 2.6);
   the line ends with an operator that begins a continuation (., ->,
   =>, <-, **, //, .., the assignment operators, the comparison
   operators, +, -, *, /, %, &, |, ^, &&, ||, <<, >>, <<=, >>=); or a
   backslash line continuation applies (Section 2.3).

2.8.  Optional Type Annotations

   A name or a parameter MAY carry a type annotation after a colon, and
   a function gives its return type after the parameters with an arrow
   (->).  Annotations are optional: a program without annotations is
   complete, and an implementation MUST NOT reject it for a missing
   annotation: it is inferred from the initialiser and later uses.
   Unannotated integers are i32 and unannotated floats
   are f64.  Where a name does carry one, the annotation is enforced:
   the value bound to that name -- by let, const, var, an assignment,
   a parameter or a return -- is stored and operated on at the
   annotated width, and a value that does not fit it panics with the
   kind OutOfRange.  An annotation never converts a value; an
   out-of-range value is an error, not a truncation.  The default
   width is enforced the same way: a value or result that does not
   fit i32 or f64 panics with OutOfRange whether or not a name is
   annotated.

      let count: i32 = 0
      var name: str = "arm"
      let maybe: i32? = null   # nullable: may be null
      let items: Vec<i32> = []
      let small: i8 = 127      # ok
      let bad: i8 = 300        # panics with OutOfRange

      fn scale(x: f64, by: i64 = 2) -> f64 {
         return x * by
      }

   A type is a name, optionally parameterised by other types:

      type = name [ "<" type *( "," type ) ">" ] *( "[]" / "?" )
           / "()"

   The built-in names are bool, char, str, i8, i16, i32, i64, i128,
   isize, u8, u16, u32, u64, u128, usize, f32, f64, (), Option, Vec,
   Tuple, HashSet, HashMap, Range, Future, Channel and Any; an
   identifier names a user or host type and, if unrecognised, is
   treated as Any.
   The primitive names in the list are keywords (Section 2.4); the
   container names are ordinary identifiers.  i8 through i128, u8
   through u128, isize and usize are the integer widths, and f32 and
   f64 are the float widths; the default width of an unannotated value
   is i32 or f64.  char names a one-element str
   (a value of any other length is OutOfRange), and () is the unit
   type of the empty tuple.  Vec, HashMap and Channel carry element
   types (Channel<i64> is the element type of chan i64, Section 3.6).
   T? is sugar for Option<T>, the nullable type of a value that may be
   null, and T[] is sugar for Vec<T>.  Suffixes apply in the order
   written, so T[]? is Option<Vec<T>> and T?[] is Vec<Option<T>>.  A
   type name followed by parenthesised arguments is a constructor of
   that type, as in Vec<i64>(), i64("42") and Point(x = 1.0)
   (Section 3.8).  The language defines no subtyping beyond its
   built-in kinds.

3.  Types and Values

3.1.  Value Model

   Types are static: every value has one type, known where it is
   written.  An unannotated name does not lack a type; it takes the
   type inferred for it (Section 2.8).  A value belongs to
   exactly one of the following kinds: null, bool, integer, float, str,
   Vec, Tuple, HashSet, HashMap, function, Future or Channel.  An
   integer is a 32-bit signed value and a float is binary64 unless a
   type annotation (Section 2.8) narrows it.  There is no implicit
   conversion between numeric kinds except where an operator states
   one; text is never silently coerced to a number and a number is
   never silently coerced to text.

   Assignment, argument passing by alias (Section 7.4) and container
   membership bind a name or a slot to a value; they do not copy it.
   Mutation of a shared value is visible through every binding to it.

3.2.  Vec, Tuple, HashSet

   A list is an ordered, mutable sequence written [a, b, c]; the empty
   Vec is written [] or [,].  A tuple is an ordered, immutable sequence
   written (a, b, c); a tuple of one element is written (a,) and the
   empty tuple is written () or (,), which is also the unit type.  A
   trailing comma is permitted in a Vec, tuple, HashSet or HashMap.  A
   set is an unordered, mutable collection of distinct values written
   {a, b, c}.  Because {} is always an empty block, the empty HashSet
   is written {,}.

3.3.  HashMap

   A dictionary is an unordered, mutable mapping written {key: value,
   ...}.  Keys are compared by value; text and integer keys are
   distinct.  A member is read with expr[key] and written with
   expr[key] = value.  The empty HashMap is written {:}; the empty
   braces {} are always an empty block, never a literal.

3.4.  Range

   A range a..b is a half-open interval from a up to but not including
   b, stepped by one; a..b:step carries an explicit step.  A range is
   an immutable value that is consumed by iteration and by slicing.  A
   trailing .. denotes an open upper bound and is meaningful only as a
   slice index.

3.5.  Future

   A future is a placeholder for a value that is not yet known.  It is
   created by spawn (Section 6.2), by an async function (Section 7.1)
   and by every device call (Section 9.3).  A future is one of three
   states: pending, resolved or failed.

   *  pending: the work it stands for has not produced a result.

   *  resolved: the work produced a value; await yields that value.

   *  failed: the work raised a panic; await re-raises it (Section
      6.8) so the failure propagates to the awaiter.

   A future carries no method that reads its value without waiting; the
   only ways to observe it are await, race, select and cancel.

3.6.  Channel

   A channel is a typed conduit for passing values between tasks.  It is
   created with chan T for an unbuffered channel, or chan T(n) for a
   channel buffered with room for n values.  The element type T is
   enforced like any annotation (Section 2.8): a sent value that does
   not fit T panics with the kind OutOfRange.

   *  Send: ch <- value, or the value-first form value -> ch, appends
      value to the channel.  On an unbuffered channel the sender
      suspends until a receiver is ready; on a full buffered channel
      it suspends until room appears.

   *  Receive: <-ch removes and yields the oldest value, suspending the
      receiver until a value is present.  Receiving from a closed
      channel yields null once it is drained and then fails closed.

   *  close(ch) marks a channel closed; further sends fail and further
      receives drain the buffer then yield null.

   A channel is first-class and may be stored, passed as an argument
   and selected upon (Section 6.4).

3.7.  Spread

   The prefix ... expands a list, tuple or set into the position where
   it stands: into a list literal, into a call's positional arguments,
   or into a binding target for destructuring (Section 8).  Spread MAY
   appear more than once in one position and MAY be mixed with single
   values.

      let tail = [3, 4]
      let all = [1, 2, ...tail]          # [1, 2, 3, 4]
      fn add(a, b, c, d) { a + b + c + d }
      add(1, ...all)                     # 1 + 2 + 3 + 4

3.8.  struct: Composite Types

   A struct declares a composite type: a named record of fields, each
   field carrying a type.  A field type is a primitive or another
   struct; the value is therefore a combination of primitives.  A
   struct value may be stored in any container -- Vec<Point>,
   HashMap<str, Point>, HashSet<Point> -- and the container rules of
   Sections 3.2 and 3.3 then apply.

      struct Point {
         x: f64
         y: f64
      }

      let p: Point = Point(x = 1.0, y = 2.0)
      let path: Vec<Point> = Vec<Point>([])
      p.x = 3.0                        # a field is a member

   A struct is a type name: it may annotate a name, a parameter or a
   return, and it is the type of every value built by its
   constructor.  The constructor is the type name followed by
   arguments; a field is given by name, as any call may bind a
   parameter (Section 7.5), or by position in declaration order.  A
   field is read and written with the member syntax of Section 5.1.
   Structs are nominal: two structs are the same type only if they are
   the same declaration.

4.  Operators and Precedence

   Operators associate as listed.  Higher precedence binds tighter.

      +----------+--------------------------------+--------------------+
      |Precedence| Operators                      | Associativity      |
      +----------+--------------------------------+--------------------+
      |1 (highest| !  ~  - (unary)  await  spawn  | right             |
      |          | <- (receive)                   |                    |
      +----------+--------------------------------+--------------------+
      |2         | **                             | right             |
      +----------+--------------------------------+--------------------+
      |3         | *  /  //  %  &  <<  >>         | left              |
      +----------+--------------------------------+--------------------+
      |4         | +  -  |  ^                     | left              |
      +----------+--------------------------------+--------------------+
      |5         | ..  ..:                       | left              |
      +----------+--------------------------------+--------------------+
      |6         | ==  !=  <  >  <=  >=  in  as   | left (chained)    |
      +----------+--------------------------------+--------------------+
      |7         | not                            | right             |
      +----------+--------------------------------+--------------------+
      |8         | and                            | left              |
      +----------+--------------------------------+--------------------+
      |9         | or                             | left              |
      +----------+--------------------------------+--------------------+
      |10        | ?  :  (ternary)                | right             |
      +----------+--------------------------------+--------------------+
      |10.5      | within (timeout)               | left              |
      +----------+--------------------------------+--------------------+
      |11        | =  +=  -=  *=  /=  &=  |=  ^=  | right (chained)   |
      |          |   <<=  >>=                    |                    |
      +----------+--------------------------------+--------------------+
      |12 (lowest| <-  -> (send)                  | left              |
      +----------+--------------------------------+--------------------+

                         Table 1: Precedence

   Chained comparison (a < b < c) and chained assignment (a = b = c)
   are evaluated left to right with the natural meaning.  Member access,
   indexing and calling (Section 5.1) bind tighter than precedence 1.

5.  Expressions

5.1.  Member Access, Indexing, Calling

   expr.name reads a member.  expr[index] indexes a list, tuple, text
   or dictionary; negative indices count from the end.  expr(args) calls
   a function or invokes a native procedure.  The three may be chained:
   device.status().state.

   A call argument is bound by position (a value) or by name (name:
   value).  A position and a name MAY appear in one call; positions
   count from zero among themselves, exactly as [RFC0004], Section 5.3
   binds CALL arguments, because a device call is encoded as a CALL.

5.2.  Optional Chaining

   expr?.name, expr?[index] and expr?(args) evaluate the chain only
   when the left operand is not null; otherwise the whole chain is null
   and no further step is taken.  Optional chaining short-circuits.

5.3.  Ternary Operator

   cond ? a : b evaluates cond; if true it evaluates and yields a,
   otherwise b.  Only one branch is evaluated.

5.4.  Comprehensions

   A comprehension builds a list, set or dictionary by iterating:

      [f(x) for x in items if p(x)]
      {f(x) for x in items if p(x)}
      {k(x): v(x) for x in items if p(x)}

   The for clause introduces the iteration variable; one or more if
   clauses filter.  At most one for clause is permitted; nesting is
   expressed by iterating over a nested structure.

5.5.  Arrow Functions

   An arrow function |args| body is an anonymous function.  With one
   parameter the bars MAY be omitted: |x| x * 2 or x => x * 2.  The
   body is an expression; arrow functions close over their lexical
   scope (Section 7.2).

      let sq = |x| x * x
      let apply = |f, xs| [f(x) for x in xs]

5.6.  Scope Views: globals and locals

   The identifier globals refers to the top-level scope and locals to
   the immediately enclosing function scope.  Reading globals.name or
   locals.name inspects a binding; assignment to them is not permitted
   through the view.  They exist so a debugger or a host hook (Section
   9.1) can inspect state without a special API.

6.  Statements, Control Flow and Concurrency

   This section defines the statements of the language.  Section 6.1
   covers separation, blocks and conditions, and the sequential control
   flow built on them; Section 6.2 the failure model; Sections 6.3 to
   6.8 the concurrency constructs; and Section 6.9 cancellation.

6.1.  Separation, Blocks and Conditions

   A statement is terminated by a newline or by one semicolon.  An
   empty statement is a syntax error; where a block must do nothing it
   is written empty, "{ }", or holds a single pass (Section 6.1.8).  A
   block is a sequence of statements enclosed in braces; it introduces
   a new lexical scope nested in the scope that encloses it.  At
   statement position "{" always begins a block, even though "{" at
   expression position begins a literal.

   Parentheses around a statement header MAY be omitted without
   changing meaning, with one exception: the counted "for" header
   (Section 6.1.6) REQUIRES them.  The subject of match (Section 6.1.2)
   is likewise always parenthesised.

   The compound statements if, elif, else, for, while, loop, do, try,
   except, finally, match, race, select, par and on open a block; so do
   fn, a case arm, an until body and the arrow body when it is a block.

   Conditions.  Every condition in this section -- those of if and
   elif, of while and do-while and of the counted for, and the guard of
   a case arm -- MUST be of type bool.  A value of any other type is
   never converted to bool: a number, a text, a container, a future or
   null in a condition is a type error, which an implementation MUST
   report before the program runs.  A test is therefore written out:
   x != null, len(xs) > 0, k in table, or an explicit conversion
   bool(x).  The operands of and, or and not are bool for the same
   reason, and the rule governs the ternary condition (Section 5.3) and
   a comprehension filter (Section 5.4) as well.

   A condition is evaluated each time control reaches it and not
   before: a while condition is tested before every iteration, a
   do-while condition after every iteration, and an if condition once
   per execution of the if.  A loop condition that is never reached --
   the condition of a do-while whose body breaks out -- is not tested.

6.1.1.  if / elif / else

      if x > 0 {
         log("pos")
      } elif x < 0 {
         log("neg")
      } else {
         log("zero")
      }

   The conditions are tested in order and testing stops at the first
   one that is true.  Exactly one branch runs: that branch, or the else
   branch when no condition holds.  The branches that are not taken are
   not evaluated.  elif and else are optional; an if with no else whose
   conditions all fail does nothing.  elif is one keyword; "else if"
   opens a second if inside the else block and means the same thing.

6.1.2.  match / case

      match (status) {
         case 0 {
            "idle"
         }
         case 1 {
            "run"
         }
         case n if n > 10 {
            "fast"
         }
         case [a, b] {
            a + b
         }
         case _ {
            "unknown"
         }
      }

   The subject is evaluated once and is written in parentheses, which
   are REQUIRED here.  The cases are tried in textual order and exactly
   one wins: the first whose pattern matches and whose guard, if any,
   is true.  There is no fall-through; the cases after the winner are
   not tried.  The value of the match is the value of the winning
   case's body, or null when no case matches, so a program that means
   to cover every case SHOULD end with case _.  At least one case is
   REQUIRED.  Patterns are:

   *  a literal: a number, text, boolean or null, matched by value;

   *  a sequence [p1, p2]: matched against a list or a tuple of the
      same length, binding the elements to the sub-patterns;

   *  a capture name: matches anything and is bound to the whole
      value; and

   *  the wildcard _: matches anything and binds nothing.

   A bare name is therefore always a capture and never a constant:
   case n binds whatever the subject is.  A capture and _ may also
   appear inside a sequence pattern.  A case MAY carry a guard, "case
   PATTERN if guard { }": the pattern is tried first and the guard is
   evaluated only when it matches, so the case is taken only when both
   hold.  A case body is a block written without a colon; a colon after
   the pattern is a syntax error.  A name bound by a pattern is local
   to the case body; where the same name is bound outside, the capture
   introduces a new binding inside the body and leaves the outer one
   untouched.

6.1.3.  while

      while n > 0 {
         n -= 1
      }

      while (n > 0) {
         n -= 1
      }

   The condition is evaluated before each iteration; the body runs
   while it is true, so a while runs zero or more times.  The loop is
   left through break (Section 6.1.8), return (Section 6.1.9), a
   failure (Section 6.2) or an until clause (Section 6.1.7).

6.1.4.  loop

      loop {
         if done() { break }
         step()
      }

   "loop { ... }" repeats unconditionally: it has no condition, runs at
   least once and is left only through break, return, a failure or an
   until clause.  It is the form for a cycle whose end is decided
   inside the body; "while true { ... }" says the same thing and is
   equally legal.

6.1.5.  do...while

      do {
         n -= 1
      } while (n > 0)

   The body runs once, then the condition is tested; the loop repeats
   while it is true, so it runs one or more times.  continue jumps to
   the condition, and break leaves the loop.  The header MAY carry an
   until clause (Section 6.1.7), normally written after the condition,
   because the body, during which events are captured, has already run
   once when the clause is reached:

      do {
         sample()
      } while running()

6.1.6.  for: Iterable and Counted

   Iterable form.  "for t in coll { ... }" binds t to each element of
   coll in turn; coll MAY be a list, tuple, set, dictionary, range or
   any iterable, and it is evaluated once, before the first iteration.
   For a dictionary the loop variable is the key, or a k, v pair may be
   bound:

      for i in [1, 2, 3] {
         log(i)
      }

      for k, v in table.items() {
         log(k, v)
      }

      for (k, v) in pairs {
         log(k, v)
      }

   The target MAY destructure, with or without parentheses; a single
   variable MAY be wrapped in a redundant pair of parentheses.  The
   target's bindings are local to the loop.  Modifying coll while the
   loop runs is not defined by this document; a program MUST NOT rely
   on what such a loop sees.

   Counted form.  "for (init; cond; update) { ... }" runs init once,
   then repeats the body while cond is true, running update after each
   iteration; the parentheses are mandatory and all three clauses MAY
   be omitted, an omitted condition being taken as true:

      for (let i = 0; i < n; i += 1) {
         log(i)
      }

      for (;;) {
         if done() {
            break
         }
      }

   The initialiser MAY be a declaration or an assignment; a name it
   declares is local to the whole loop, header and body alike.  "let"
   is RECOMMENDED because "var" writes to the root scope, where a
   repeated declaration in the same scope is an error.  continue still
   executes the update clause before the next condition test; break
   leaves the loop.  Both forms MAY carry an until clause
   (Section 6.1.7).

6.1.7.  until: Event-Gated Loop Exit

   The until clause applies to every loop head uniformly -- while,
   loop, do-while and both forms of for -- and appears at most once on
   a head.  It gates a loop on an event captured in the loop's own
   cycle, instead of, or in addition to, its condition:

      while <cond> until "event.foo" [as bar] { ... }
      loop     until "event.foo" [as bar] { ... }
      for t in coll until "event.foo" [as bar] { ... }
      for (init; cond; update) until "event.foo" [as bar] { ... }
      do { ... } while <cond> until "event.foo" [as bar] { ... }
      do { ... } until "event.foo" [as bar] { ... } while <cond>

   A cycle is one iteration of the loop: the running of the body, and
   for a counted loop the update and the condition test.  until opens
   its subscription when the loop is entered and closes it when the
   loop is left; every matching event that arrives during a cycle is
   appended to that cycle's buffer, and the buffer is discarded when
   the cycle ends.  until does NOT wait: at the end of the cycle it
   inspects the buffer and

   *  when the cycle captured no matching event, the until body is
      skipped and the loop proceeds straight to its next iteration or,
      for while and the counted for, to the next condition test;

   *  when the cycle captured one or more matching events, the until
      body runs once, with the earliest of them -- the first captured
      -- bound as below.  Later events of the same cycle are ignored
      by until.

   What the until body does then decides the loop's fate:

   *  (fall-through) if the until body finishes without a break or a
      continue, it is as if a break were inserted at its end: the loop
      is left.  To leave directly when an event occurred, with no
      action, write an empty until body: } until "event.foo" { };

   *  continue: control returns to the loop to run its next iteration,
      which opens a fresh cycle buffer;

   *  break: the loop is left immediately, as it would be from the loop
      body.

   For a do-while loop the until clause normally follows the condition,
   for the reason given in Section 6.1.5.  Written before the condition
   instead, it is checked first: the until check precedes the condition
   test, so an event taken in the body may end the loop before the
   condition is ever evaluated.

   The topic is a string, an array of strings, or a single string using
   OCP topic wildcards [RFC0004], Section 6.5.2, where "+" matches one
   level and "#" every level beneath it.  Each element of an array may
   be a strict topic or a wildcard, and the two MAY be mixed freely;
   several topics or wildcards may fire in one cycle, and the
   first-captured event is the one bound, as above:

      loop until ["motor.a", "motor.+"] as e { ... } # strict + wildcard
      loop until "sensor.+.temp"       as e { ... }  # OCP wildcard

   The optional as bar binds the first-captured event's payload to bar
   for the duration of the until body; the body may read bar's members.
   When as bar is omitted the payload is bound to the implicit name _,
   as in on (Section 6.7) and wait (Section 6.8).  The binding is local
   to the until body; reading the captured value through _ is not
   recommended, and a program SHOULD bind a name with as instead.

   An until clause never changes the loop's own condition; the loop may
   also be left through that condition, return, break or a failure.
   The subscription behind an until clause belongs to the loop's task
   and is therefore cancelled with it (Section 6.9); a panic inside the
   until body propagates to the loop's task.

6.1.8.  break, continue and pass

   "break" leaves the innermost enclosing breakable construct: a loop,
   or the match (Section 6.1.2) when the break stands in one of its
   case bodies.  The blocks of if and try and the arms of select do not
   trap break; it crosses them to reach that construct, so a break in a
   select arm inside a loop leaves the loop.  "continue" starts the
   next iteration of the innermost enclosing loop: in the counted for
   it runs the update clause first, in a do-while it jumps to the
   condition, and in an until body it returns control to the loop
   (Section 6.1.7).  A break or a continue with nothing to leave is a
   syntax error.

   "pass" is a no-op statement: it does nothing, and exists so that a
   branch which is meant to do nothing says so.  An empty block is
   likewise legal where a block is required.

6.1.9.  return

   "return" with a value returns it; "return" without a value yields
   null.  A return propagates out of any nesting of blocks, loops and
   try statements: an except clause does not intercept it, while a
   finally clause still runs on the way out.  A return inside a finally
   clause supersedes the one in flight.  If a function body finishes
   without an explicit return, the value of its last statement is
   returned; if that statement has no value, the function returns null.
   Inside a task (Section 6.3), return resolves the task's future with
   that value.  A return at the top level of a program terminates the
   program.

6.2.  Failure: panic, try and except

   panic kind raises a failure carrying a kind, which is a text value
   naming the class of error; an optional second argument carries a
   human-readable message.

      panic "HardwareError" "motor stalled"

   A panic abandons the statement that raised it: the statements after
   it in the same block do not run.  try { body } except Kind as e {
   handler } finally { cleanup } catches a panic raised by body whose
   kind equals Kind, exactly; the optional as e binds the panic object,
   whose members are kind and message.  A try MAY carry several except
   clauses, which are tried in textual order and of which at most one
   runs; a bare except catches any kind and, when present, SHOULD come
   last, since a clause after it could never run.  An except clause
   does not catch a panic raised by another except clause, and a panic
   raised in finally supersedes the failure in flight.  finally runs
   whether the body panicked or not, and also when the body is left by
   return, break or continue.

   A panic that no try catches propagates to the nearest enclosing task
   and fails its future (Section 6.3).  An uncaught panic in a handler
   started by on (Section 6.7) is reported on the runtime topic
   core.error [RFC0004], Section 9.2.1, and the subscription survives.
   An uncaught panic in the top-level task ends the program and is
   reported on core.error.

   The kinds a program MUST be prepared to catch are the OCP error-code
   names of Section 9.5 and the built-in kinds Timeout, Cancel and
   OutOfRange (Section 2.8).

6.3.  Tasks, spawn and await

   A task is a unit of concurrent execution.  The program itself runs
   as one task.  New tasks are started with spawn:

      let f = spawn expensive_computation(a, b)

   spawn evaluates its operand in a new task and returns a future
   (Section 3.5) immediately; the caller's task is not suspended.  The
   operand is normally a call: its arguments are evaluated in the
   current task and the call itself runs in the new one.  The future
   resolves with the task's result or fails with its panic.  Discarding
   the future does not cancel the task.

   await suspends the current task until a future resolves, then yields
   its value or re-raises its panic:

      let result = await f
      let temp = await sense("temp")      # a device call is a future

   A future keeps its outcome: awaiting one that has already resolved
   yields the same value again, and awaiting one that has already
   failed re-raises the same panic.  await may appear in any task,
   including the top-level one.  A task that awaits several futures
   does so one at a time; to await them together, spawn each and race
   (Section 6.5) or select (Section 6.6) over the futures, or run them
   as the branches of a par block (Section 6.4).

   The within operator bounds an await.  await f within d suspends
   until f resolves or until d seconds pass, whichever is first; if the
   timeout wins the await yields null and f is cancelled.  Without
   await, expr within d is sugar for race { expr; sleep d }: it races
   the value-producing expression against a timeout and yields the
   expression's value, or null if the timeout wins.

   A task that finishes is joined automatically; its result is held by
   its future for as long as the future is reachable.  A top-level
   program does not end until every task it started, directly or
   transitively, has resolved, failed or been cancelled.

6.4.  par: Parallel Blocks

   par runs several statements at once and waits for all of them to
   finish.  Each top-level statement in a par block starts as its own
   task, concurrently with the others and with the enclosing task; par
   then suspends the enclosing task until every branch has resolved,
   panicked or been cancelled:

      par {
         move_arm("home")
         await sense("grip")      # each branch may await
         log_status()
      }

   A branch is any statement.  The last statement of a branch that is
   an expression yields that value, and par yields an array of the
   branch values in textual order; a branch with no value contributes
   null.  A name declared with let or const inside a branch is local to
   that branch's task and is not visible outside it, and so is a name
   bound by as or by the implicit _.

   Branches share the enclosing scope, so a branch MAY read and assign
   a variable declared outside the par block.  Such a shared assignment
   is a data race when two or more branches write the same variable;
   the result is then indeterminate and a program MUST NOT rely on it.
   Reading a variable another branch may write, unsynchronised, is
   likewise a data race.

   par joins all branches: it does not return until the last has
   resolved.  If a branch panics, the other branches are cancelled
   (Section 6.9) and par re-raises the panic of the branch that appears
   first in the block among those that panicked.  A panic in a branch
   reaches the enclosing task as if the branch had run there.

   If the enclosing task is cancelled while par waits, par cancels
   every branch and the cancellation surfaces as a Cancel failure in
   the enclosing task (Section 6.9).  par takes no until clause; the
   gating of a loop is the province of Section 6.1.7.

6.5.  race: Racing Outcomes

   race runs several branches concurrently and keeps the value of the
   first branch that resolves; every other branch is cancelled.

      let winner = race {
         sense("left")
         sense("right")
         status()
      }

   The block contains one or more expressions or statements; each is
   started as a task.  race returns the value of the first branch that
   resolves.  Branches that are still pending when a winner resolves
   are cancelled (Section 6.9).  A branch that is a statement with no
   value resolves with null, and null is then a value that can win the
   race; a timeout arm expressed as sleep d wins the same way.  If
   every branch fails, race re-raises the panic of the branch that
   appears first in the block among those that failed.

   race is the construct for the common robotic question "which of
   these reaches a result first": the faster sensor, the first
   actuator to confirm, or a status reply before a timeout.  A timeout
   is written either as a sleep branch of the race or, more compactly,
   with within (Section 6.3).

6.6.  select: Waiting on Events, Channels and Time

   select waits for the first of several independent outcomes and runs
   the arm that won.  Each arm is one of:

      on <topic>:     wait for the next EVENT on the topic
      recv ch:        wait to receive one value from channel ch
      send v -> ch:   wait until ch can accept a send of v
      after <dur>:    wait for dur seconds (a timeout arm)
      default:        run immediately if no other arm is ready

   The arms are written as a block; each arm is a label followed by a
   block.  A select with no arm would wait forever, so a program SHOULD
   write at least one; at most one default arm is permitted:

      select {
         on "device.fault" as fault {
            latch(fault)
            stop_all()
         }
         recv cmd_chan as cmd {
            handle(cmd)
         }
         after 2.0 {
            retry()
         }
      }

   An arm whose guard is ready runs its block; the select then
   completes and yields the value the block produced, or null.  If more
   than one arm is ready at the same instant, exactly one is chosen;
   the choice among ready arms is implementation-defined, except that
   default is chosen only when no other arm is ready.  A select with no
   ready arm and no default suspends the current task until one arm
   becomes ready.  After the chosen arm's block has run, the other arms
   are abandoned; pending sends or receives in them are not completed.

   In a send arm the value is computed and the send is performed when
   the arm is chosen, immediately before its block runs; an arm that is
   not chosen sends nothing.  An after arm is a timer of the same kind
   as sleep (Section 6.8), started when the select begins to wait.

   on in a select is a one-shot wait for a single event; the persistent
   subscription form is on (Section 6.7).  The event data is bound to
   an explicit as name after the topic; without one it is bound to the
   implicit name _.  A recv arm binds the received value the same way.
   Reading the captured value through _ is not recommended; a program
   SHOULD bind a name with as and read that instead.

6.7.  on: Persistent Event Subscriptions

   on subscribes to a topic for the life of the program or until the
   subscription is cancelled, and runs a handler task for every event
   that arrives:

      let sub = on "device.fault" as ev {
         latch_fault(ev.name)
      }

   Each arriving EVENT for a matching topic starts a new task running
   the handler; handler tasks run concurrently with the main flow and
   with one another.  The handler names the event data with as ev or
   uses the implicit binding _.  Reading the captured value through _
   is not recommended; a program SHOULD bind a name with as and read
   that instead.  If the handler panics, the panic is reported on the
   runtime topic core.error [RFC0004], Section 9.2.1, and the
   subscription survives.

   on is an expression: it yields a subscription handle, which a
   program SHOULD bind so that it can cancel the subscription later.
   sub.cancel() sends UNSUBSCRIBE [RFC0004], Section 5.6, so that no
   further event starts a handler; handler tasks already running are
   cancelled (Section 6.9).

   The topic MAY contain the wildcards + and # exactly as [RFC0004],
   Section 6.5.2 defines: "device.+" matches one level, "device.#"
   matches every level beneath device.

6.8.  Timing: sleep and wait

   sleep dur suspends the current task for dur seconds, then yields
   null.  dur is a number; fractional seconds are permitted.  sleep
   never spins: the task is removed from the run queue for the
   duration.

      sleep 0.5          # pause half a second

   wait topic suspends the current task until the next EVENT on topic
   arrives and yields its data; it is sugar for a one-arm select
   (Section 6.6):

      let ev = wait "device.status"
      let fault = wait "device.fault"

   The block form runs its body once with the payload bound by as, or
   to _ when as is omitted.  Reading the captured value through _ is
   not recommended; a program SHOULD bind a name with as and read that
   instead.

      wait "device.fault" as fault {
         latch_fault(fault.name)
      }

   wait is a one-shot subscriber: it does not outlive the call and
   does not require an explicit unsubscribe.  A wildcard topic is
   accepted and matches the first concrete event it receives.  A wait
   that is given no way to end -- no event and no timeout -- suspends
   until one arrives; a bounded wait is written with the after arm of
   select or, for a future, with within (Section 6.3).

6.9.  Cancellation

   cancel(future) requests cancellation of the task behind a future or
   of a subscription handle.  For a future that is a device CALL it is
   implemented by the cancel procedure of the Core Profile: the
   implementation sends CALL {name: "cancel", args: {"id": <the CALL's
   id>}} to the device, which answers whether the cancellation took
   (RFC0004, Sections 5.4 and 9.1.4).  Cancellation is cooperative for
   a local task: the task observes the request at the next await,
   sleep, select or device call and then stops; work already dispatched
   to a device is not recalled, because a CALL that has left the host
   is allowed to run to its RESULT (RFC0004, Section 6.4.4), which the
   cancel procedure then reports as not taken.  A cancelled task
   settles its future as failed with the kind Cancel.  Cancelling a
   future that has already settled, or a subscription that is already
   cancelled, does nothing.

   race (Section 6.5) cancels the losers, select (Section 6.6)
   abandons the arms it did not choose, par (Section 6.4) cancels its
   branches when the enclosing task is cancelled, and a handler started
   by on (Section 6.7) is cancelled with its subscription; all four use
   the same cooperative mechanism.

   A task that ignores cancellation -- one that never awaits, sleeps,
   selects or calls a device -- cannot be stopped by the host; a
   program SHOULD NOT write such a task on a long-running path.

7.  Functions, Scope and Arguments

7.1.  Definition and Call

   A function is defined with fn name(params) { body } or as an arrow
   (Section 5.5).  Parameters are names; a parameter MAY carry a
   default.  A call binds arguments by position or by name (Section
   5.1).  A function returns the value of its last expression or of an
   explicit return; a function that falls off the end returns null.

   An fn MAY be prefixed with async: an async function returns a future,
   not a value: calling it starts a task (as spawn would, Section 6.2)
   and yields a future that resolves with the function's return value or
   fails with its panic.  The future is observed with await, race or
   select exactly as any other, and is cancelled with the same
   cooperative mechanism (Section 6.7).

7.2.  Closures

   A function closes over the lexical bindings visible where it is
   defined.  A mutation of a closed binding is visible to every closure
   that shares it.  A closure is a first-class value and may be stored,
   passed and spawned.

7.3.  Scope and Declaration

   Scopes nest: a block opens a child scope; a name is resolved in the
   nearest enclosing scope that declares it.  let and const declare a
   binding in the current scope; const forbids reassignment and is a
   runtime error to assign to.  var declares a binding in the
   top-level scope from anywhere (a global), matching the globals view
   of Section 5.6.  A name used before it is declared in its scope is a
   runtime error, not a silent null.

7.4.  Argument Passing by Alias

   Arguments are passed by alias: the parameter names the same value
   the caller passed, so a mutation the function makes is visible to the
   caller.  Reassigning the parameter to a new value does not change the
   caller's binding; to return a changed container the function returns
   it.

7.5.  Defaults, Named Arguments and the Parameter Sink

   A parameter name = expr gives a default, evaluated at call time in
   the function's scope.  A call MAY bind a parameter by name.  The
   sink parameter ...rest collects the positional arguments not bound
   by a named parameter into a list, and :::kw collects the named
   arguments not bound by a parameter into a dictionary.  The token
   ::: appears only in a parameter list.

      fn log(level = "info", ...rest) { ... }
      fn conf(host, ...opts, :::kw) { ... }

8.  Destructuring Assignment

   A binding target may be a pattern that takes apart a value:

      let (x, y) = point            # tuple or list of two
      let [a, b, ...rest] = items   # list, with a tail
      let {name, unit} = sensor     # dictionary by key

   Destructuring works in let, const, var, the for variable, the
   parameter list.  A failed match -- too few
   elements, a missing key -- panics with the kind BadMatch.  A key
   absent from the source dictionary may be given a default with name =
   expr in the pattern.

9.  Host Interface, OCP Binding and Hardware

   A host embeds the language and supplies the machine-facing
   operations by speaking [RFC0004].  This section is the contract
   between a program and the host.  Every procedure a program invokes on
   a device becomes a CALL [RFC0004], Section 5.3; every value a
   device returns becomes a RESULT [RFC0004], Section 5.4; every
   notification becomes an EVENT [RFC0004], Section 5.5.

9.1.  Native Functions

   The host provides the built-in procedures of Section 9.3 and 9.4 and
   the session operations of Section 9.2.  A host MAY expose further
   native functions under names it chooses, but it MUST NOT shadow the
   keywords of Section 2.4 or the built-ins of this section.  A host
   hook is any native function the host registers; the language places
   no requirement on its body beyond that it returns a future when it
   performs I/O.

9.2.  Sessions and connect()

   A session is an open [RFC0004] connection.  The host opens one
   default session at start; connect() opens another and returns a
   session object.  The session object carries the peer's agreed
   capabilities (rpc, pubsub, blobtun) [RFC0004], Section 8 and the
   security mode in force.

      let dev = connect("ocp://arm.example:6286")
      let sec = connect("ocp-fls://arm.example", {
         algs: {enc: ["chacha20-poly1305"], itg: ["crc32"]}
      })
      let tls = connect("ocps://arm.example:16286", {
         tls: {server: "arm.example"}
      })

   The URI scheme selects the protection in force:

      +-----------+----------+----------------------------------+
      |Scheme     |Port      |Protection                         |
      +-----------+----------+----------------------------------+
      |ocp://     |6286      |Cleartext [RFC0004], Section 7.4  |
      +-----------+----------+----------------------------------+
      |ocp-fls:// |6357      |Frame-layer security [RFC0009]     |
      +-----------+----------+----------------------------------+
      |ocps://    |16286     |Secure transport [RFC0010], ALPN  |
      |           |          |"ocp/1"                           |
      +-----------+----------+----------------------------------+

                         Table 2: Session Schemes

   connect() performs the [RFC0004] handshake: it sends HELLO with its
   capabilities and, for a secured scheme, the members that [RFC0009]
   or [RFC0010] require, and waits for WELCOME.  If the security mode
   the caller required is not confirmed by WELCOME, connect() closes
   the session and panics with the kind the negotiation reports (for
   example Unauthorized or Unsupported); an Air peer [RFC0011] silently
   closes a secured session, which the host surfaces as SessionExpired.

   A device call may name a session: sense("temp", @dev) issues the CALL
   on dev instead of the default session.  The @ prefix is the session
   selector; when omitted the call uses the default session.

9.3.  Core Profile Bindings

   The Core Profile instructions of [RFC0004], Section 9.1 are available
   as built-in asynchronous functions.  Each returns a future that
   resolves with the RESULT value or fails with the RESULT error.

      +------------+-----------------------------------+-----------+
      |Function    |Maps to                            |Returns    |
      +------------+-----------------------------------+-----------+
      |ping()      |CALL ping                          |{t, time}  |
      +------------+-----------------------------------+-----------+
      |status()    |CALL status                        |state map  |
      +------------+-----------------------------------+-----------+
      |metadata()  |CALL metadata                      |five arrays|
      +------------+-----------------------------------+-----------+
      |sense(n)    |CALL sense (name = n)              |reading    |
      +------------+-----------------------------------+-----------+
      |actuate(n,  |CALL actuate (name = n, rest by    |null       |
      |   ...)     |position or name)                  |           |
      +------------+-----------------------------------+-----------+
      |get_param(n)|CALL get_param (name = n)          |value      |
      +------------+-----------------------------------+-----------+
      |set_param(n,|CALL set_param (name = n, value =  |null       |
      |   v)       |v)                                 |           |
      +------------+-----------------------------------+-----------+

                      Table 3: Core Profile Bindings

   Because each call is a future, awaiting it is the norm:

      let t = await sense("temp", @dev)
      await actuate("gripper", force = 20)

   An unknown name, an argument form the peer refuses, or a failure
   inside the procedure is delivered in RESULT with ok false; the host
   fails the future with the error's kind (Section 9.5), which the
   program catches with except.  This matches [RFC0004], Section 6.4.2:
   a refused call is an outcome, never an ERROR frame.

   metadata() returns {instructions, sensors, actuators, params,
   events} exactly as [RFC0004], Section 9.1.2 specifies; a program
   SHOULD read it once after connect() and re-read it when the
   core.metadata topic fires (Section 6.5).

9.4.  Publish/Subscribe Bindings

   SUBSCRIBE, EVENT and UNSUBSCRIBE [RFC0004], Sections 5.5 to 5.6 are
   exposed by on (Section 6.5) and wait (Section 6.6).  The topics a
   program may use are those of [RFC0004], Table 21: the device.*
   topics published by the peer and the core.*, rpc.*, pubsub.* and
   blobtun.* topics raised by the runtime.  A pseudo-topic (one the
   runtime raises, not the peer) is handled exactly like a PubSub topic
   -- the same on, the same handler, the same subscribe -- because to
   the language the two are indistinguishable [RFC0004], Section 9.2.1.

   Publishing from the program side is the call publish(topic, data):
   it sends an EVENT on the session.  A program publishes only under a
   name it is entitled to, that is, a name it owns or one under the
   private x. prefix.

9.5.  Error Model and OCP Error Codes

   A future fails with a kind.  The kind is one of two origins.  An
   application failure arrives in RESULT as {kind, message}; the host
   uses that kind verbatim.  A protocol failure arrives as an ERROR
   frame [RFC0004], Section 5.11; the host maps its code to the name of
   [RFC0004], Appendix A:

      +--------+-------------------+-------------------------------+
      |Code    |Kind               |Meaning                        |
      +--------+-------------------+-------------------------------+
      |0x0000  |Internal           |Internal error.                |
      +--------+-------------------+-------------------------------+
      |0x0001  |BadMagic           |Magic octets are wrong.        |
      +--------+-------------------+-------------------------------+
      |0x0002  |BadVersion         |Protocol version unsupported. |
      +--------+-------------------+-------------------------------+
      |0x0003  |HelloExpected      |First frame was not HELLO.     |
      +--------+-------------------+-------------------------------+
      |0x0004  |UnknownType        |Message type unknown.          |
      +--------+-------------------+-------------------------------+
      |0x0005  |BadPayload         |Payload not decodable CBOR.    |
      +--------+-------------------+-------------------------------+
      |0x0006  |PayloadTooLarge    |Payload over the limit.        |
      +--------+-------------------+-------------------------------+
      |0x0007  |SessionExpired     |Session no longer usable.      |
      +--------+-------------------+-------------------------------+
      |0x0008  |Unsupported        |Feature not supported.         |
      +--------+-------------------+-------------------------------+
      |0x0009  |RateLimited        |Peer is rate limited.          |
      +--------+-------------------+-------------------------------+
      |0x000A  |Busy               |Peer busy or call timed out.   |
      +--------+-------------------+-------------------------------+
      |0x000B  |Unauthorized       |Auth missing, wrong or unusable|
      +--------+-------------------+-------------------------------+
      |0x000C  |NoTunnel           |Tunnel unknown or not open.    |
      +--------+-------------------+-------------------------------+
      |0x000D  |TunnelReset        |Tunnel reset or offset bad.    |
      +--------+-------------------+-------------------------------+
      |0x000E  |Decompress         |Compressed payload malformed.  |
      +--------+-------------------+-------------------------------+

                   Table 4: OCP Error Code Mapping

   These names are reserved: a program MUST NOT define an application
   error of the same name.  The built-in kinds Timeout (a select after
   or an await within that expired) and Cancel (a cancelled task) are
   also reserved.  Codes 0x000F and above belong to [RFC0009] and are
   mapped the same way when that extension is in force.

9.6.  Security Modes: [RFC0009] and [RFC0010]

   Three protections are available, and they are alternatives, never
   layers ([RFC0004], Section 1):

   *  None.  ocp:// with no extension.  The session is cleartext; the
      host sets no session flag beyond what the peer agrees.

   *  Frame-layer security [RFC0009].  ocp-fls:// (port 6357).  The
      host offers the algs of [RFC0009], Section 9: enc, itg and ztr,
      each a most-preferred-first list, and requests the "ext" header.
      A primitive is switched on only when WELCOME confirms a name the
      host offered; silence never switches one on.  If the host requires
      a primitive WELCOME does not confirm, connect() panics
      Unsupported and closes, as [RFC0009], Section 9 directs.  F_ENC is
      session scope; F_ITG and F_ZTR are per-frame and are applied by
      the host, not by the program.

   *  Secure transport [RFC0010].  ocps:// (port 16286, ALPN "ocp/1").
      The whole session runs inside TLS, DTLS or QUIC.  The host
      performs the handshake and validates the peer certificate; the
      program supplies the server name and, when the deployment needs
      it, the pre-shared key.  The language sees one OCP session
      regardless of which transport carries it.

   A program selects the mode only by the URI scheme and the options it
   passes to connect(); it never toggles individual flags.  The host
   reports the agreed mode through the session object's security member.

9.7.  The Air Subset: [RFC0011]

   An Air device [RFC0011] is an ordinary OCP peer that implements a
   constrained subset.  The language is unchanged when it talks to Air;
   the host honours the subset transparently:

   *  An Air peer refuses ocp-fls:// and ocps:// sessions and closes
      them; talk to it with ocp:// ([RFC0011], Section 7).

   *  Compression (F_COMP) is never used with Air, and the frame
      security of [RFC0009] is absent ([RFC0011], Section 3).

   *  Air's max_payload is at most 1024 octets ([RFC0011], Section 10).
      A program SHOULD keep each call's arguments and each event's data
      small; the host panics PayloadTooLarge if it would exceed the
      peer's limit.

   *  The error codes 0x0000 to 0x000E are reused unchanged
      ([RFC0011], Section 6); the same kinds of Table 4 apply.

   *  An Air device is reached over a stream (UART, USB-CDC or TCP);
      ACK and F_ACK are not used ([RFC0011], Section 4).  The language
      does not see this difference.

   A script written for a full peer runs against an Air peer by
   intersection: whatever the Air peer does not offer is simply absent,
   and the same metadata() call reveals it.

9.8.  Instance Meta Object

   The host exposes one meta object, octo, carrying the interpreter and
   session state:

      +-----------+------------------------------------------+
      |Member     |Meaning                                   |
      +-----------+------------------------------------------+
      |octo.version|Language and protocol versions.          |
      +-----------+------------------------------------------+
      |octo.sessions|Vec of open session objects.          |
      +-----------+------------------------------------------+
      |octo.default|The default session object.            |
      +-----------+------------------------------------------+
      |octo.now()  |Wall-clock seconds (f64).                |
      +-----------+------------------------------------------+
      |octo.sleep  |Alias of the sleep statement as a        |
      |           |callable.                                 |
      +-----------+------------------------------------------+

                      Table 5: Meta Object octo

   Writing octo.mock = true (Section 2.4) is permitted and is the only
   way a program influences host behaviour out of band; a host MAY
   interpret it as a request to substitute a simulated peer.

9.9.  Name Resolution Order

   A name is resolved in this order: the current block scope; enclosing
   function scopes outward; the top-level scope; the built-ins of
   Sections 9.3 and 9.4; the meta object octo; then the host's native
   functions.  A name that resolves nowhere is a runtime error, not a
   silent null.

10. Library and External Objects

10.1. Operations on Values

   Lists, tuples, sets and dictionaries support len, in (membership),
   iteration and indexing.  Text supports indexing, slicing, len, + and
   the formatting of Section 10.4.  Numbers support the arithmetic of
   Section 4.  Functions are values and support calling only.

10.2. Standard Library Functions

   The standard library has a core and an extension; only the core is
   defined here, and an extension part MAY be added later.  Only the
   core library MAY name a function after a keyword where the context
   is unambiguous; a program MUST NOT.  The core library is small and
   pure; the only functions that do I/O are the three at the end.  The
   pure part is: abs, min, max, sum, len, range, sorted, reversed,
   zip, enumerate, map, filter, any, all, type, keys, values, items,
   and the channel primitives chan, close, send, recv.  Every
   primitive type but () names a conversion function: bool, char, str,
   i8, i16, i32, i64, i128, isize, u8, u16, u32, u64, u128, usize, f32
   and f64 each take one value and yield that type; a conversion that
   does not fit panics with the kind OutOfRange (Section 2.8), so
   i8(300) fails rather than truncates.  Three functions perform
   simple line I/O: print writes each argument, formatted by Section
   10.4 and separated by a space, to standard output followed by a
   newline; eprint does the same on standard error; input reads one
   line from standard input and yields it without the trailing
   newline, or null at end of input.  A host MAY add more but MUST
   NOT remove or rename these.

10.3. Modules

   import name brings a module's bindings into scope; from name import
   a, b brings named bindings.  A module is a separate compilation unit
   the host loads; the language defines no module format, only the
   import syntax.  A cyclic import is a load-time error.

      import mod
      import a.b.c
      import a.b.c as alias
      import m1, m2 as other
      from mod import name
      from mod import name as other, second

   A dotted module name first resolves to a source module; if none
   exists, a library module supplied by the implementation is imported.
   Importing binds the module object; a dotted name binds nested
   namespaces so that "a.b.c.f()" is valid.  A name bound by import may
   be reassigned like any other binding.  There is no wildcard import:
   every imported name is written explicitly.

10.4. String Formatting

   The formatting used by interpolated strings (Section 2.6) and by
   str(x) is: null -> "null", booleans -> "true"/"false", numbers in
   their shortest round-tripping form, text as itself, lists and
   tuples as [a, b], sets as {a, b}, dictionaries as {k: v}.  A value
   with a fmt member MAY supply its own text form.  The ${...} marker
   of an interpolated string accepts any single-line expression that
   contains no meaningful braces.  A format spec, written after a
   colon, follows only on a bare variable or on an expression enclosed
   in parentheses; any other expression MUST be parenthesised
   to carry one, so a spec is never ambiguous.  The spec is ${x:spec}
   where spec is

      [[fill]align][sign]["#"]["0"][width]["." precision][type]

   align is <, ^ or > for left, centre or right, and the character
   before it is the fill; sign is + or -; # adds the 0x, 0o or 0b
   prefix; 0 pads with zeros; width is a minimum field width;
   precision is the number of fraction digits for a float (or a
   maximum length for text); type is one of b, o, x, X, e or E.
   Numbers default to right alignment and text to left; the default
   fill is a space.  Examples:

      `rate ${rate:.2}`      # "rate 3.14"
      `id [${id:6}]`         # "id [    42]"
      `id [${id:<6}]`        # "id [42    ]"
      `id ${id:06}`          # "id 000042"
      `n ${n:#06x}`          # "n 0x002a"
      `na ${name:.3}`        # first three characters
      `sum ${(a + b):.2}`    # spec on a parenthesised expression

11. Error Model and Diagnostics

   Diagnostics fall into three classes: lexical (Section 2), syntactic
   (this document's grammar) and runtime (a panic, Section 6.8).  A
   lexical or syntactic error MUST stop the program before any
   statement runs.  A runtime error is a panic carrying a kind and a
   message; the built-in kinds are those of Sections 9.5 and 6.8.

   A conforming implementation reports each diagnostic with a position
   (line and column) and a message in English.  It MUST NOT proceed past
   a lexical or syntactic error by guessing, and it MUST NOT suppress a
   panic it cannot attribute.

12. Complete Example

   The example below drives a two-wheeled arm: it reads both encoders
   concurrently, races a gripper close against a status timeout,
   subscribes to faults for the life of the run, and loops on commands
   arriving over a channel.

      connect("ocp://arm.local:6286")

      # Latch every fault for the whole program.
      on "device.fault" as ev {
         log("fault", ev.name)
      }

      # Read both encoders at once; await them together.
      let lf = spawn sense("enc.left")
      let rt = spawn sense("enc.right")
      let left = await lf
      let right = await rt

      # Race the gripper against a two-second status reply.
      let outcome = race {
         actuate("gripper", force = 20)
         status() within 2.0
      }
      if outcome == null {
         log("warn", "gripper slow; status won the race")
      }

      # Command loop: first ready arm wins.
      let cmd_chan = chan str(4)
      loop {
         select {
            recv cmd_chan as cmd {
               if cmd == "halt" { break }
               await actuate("drive", cmd)
            }
            on "device.fault" {
               await actuate("drive", stop = true)
            }
            after 30.0 {
               await actuate("led", blink = 1)
            }
         }
      }

      # The same loop, ended cleanly by a shutdown event instead of a
      # channel command, using until:
      loop {
         await step()
      } until "shutdown.requested" as cmd {
         if cmd.soft { continue }   # soft stop: keep stepping
         break                      # hard stop: leave the loop
      }

      # One-shot wait for the next status report.
      let st = wait "device.status"
      log("state", st.state)

   The expression status() within 2.0 is sugar for race { status();
   sleep 2.0 }; if the timeout arm wins, the result is null and the
   status future is cancelled.  on "device.fault" appears twice: once as
   a program-lifetime subscription and once inside select as a one-shot
   wait; both are legal and independent.

13. Security Considerations

   OctoScript is a control language; its safety is the safety of the
   session it drives.  Under ocp:// the session is cleartext and MUST
   NOT cross an untrusted network ([RFC0004], Section 12, [RFC0011],
   Section 12).  A deployment that needs confidentiality or integrity
   uses ocp-fls:// [RFC0009] or ocps:// [RFC0010]; the language selects
   these by URI only and never downgrades a required protection.

   A panic in an event handler does not tear down the subscription, but
   an uncaught panic in the top-level task ends the program; a host
   SHOULD run a supervisor that re-establishes the session on
   SessionExpired rather than leaving the machine uncommanded.  A task
   that ignores cancellation (Section 6.7) cannot be stopped; a program
   that commands a machine MUST await, sleep or select on a bound, so
   the host can cancel it on shutdown.

   User-supplied scripts are code: importing a module or calling a host
   native function is the same trust decision as running any program,
   and a host that loads untrusted scripts MUST sandbox them.

Appendix A. Collected Grammar (ABNF)

   This appendix is informative.  It collects the syntax in one place;
   the prose sections are normative.

      program      = stmt *( [newline] stmt ) [newline]

      stmt        = let-stmt / const-stmt / var-stmt / expr-stmt
                  / if-stmt / for-stmt / while-stmt / loop-stmt
                  / try-stmt / match-stmt / return-stmt / break-stmt
                  / continue-stmt / panic-stmt / pass-stmt
                  / spawn-stmt / race-stmt / par-stmt
                  / select-stmt / wait-stmt
                  / assign-stmt / struct-def / fn-def

      expr        = send-expr / ternary
      send-expr   = ternary ( ( "<-" / "->" ) ternary )
      ternary     = within-expr [ "?" within-expr ":" within-expr ]
      within-expr = or-expr [ "within" or-expr ]
      or-expr     = and-expr *( "or" and-expr )
      and-expr    = not-expr *( "and" not-expr )
      not-expr    = "not" not-expr / cmp-expr
      cmp-expr    = add-expr *( cmp-op add-expr )
      add-expr    = mul-expr *( ( "+" / "-" / "|" / "^" ) mul-expr )
      mul-expr    = pow-expr *( ( "*" / "/" / "//" / "%"
                  / "&" / "<<" / ">>" ) pow-expr )
      pow-expr    = unary-expr [ "**" pow-expr ]
      unary-expr  = ( "!" / "~" / "-" / "await" / "spawn"
                  / "<-" ) unary-expr / postfix-expr
      postfix-expr= primary *( "." name / "[" expr "]" / call / "?." )
      call        = "(" [ call-arg *( "," call-arg ) ] ")"
      call-arg    = name ":" expr / expr

      spawn-stmt  = "spawn" expr
      race-stmt   = "race" block
      par-stmt    = "par" block
      select-stmt = "select" block
      select-arm  = ( "on" topic [ "as" name ] block )
                  / ( "recv" chan [ "as" name ] block )
                  / ( "send" expr "->" chan block )
                  / ( "after" expr block )
                  / ( "default" block )
      # a recv arm binds the received value to _ or to the as name
      wait-expr   = "wait" topic
      wait-stmt   = "wait" topic [ "as" name ] block
      on-expr     = "on" topic [ "as" name ] block
      chan        = postfix-expr
      # on yields a subscription handle; wait yields the event payload
      sleep-expr  = "sleep" expr
      cancel-stmt = "cancel" expr

      if-stmt     = "if" expr block *( "elif" expr block )
                  [ "else" block ]
      while-stmt  = "while" expr block until-clause?
      loop-stmt   = "loop" block until-clause?
      do-stmt     = "do" block "while" expr until-clause?
                  / "do" block until-clause "while" expr
      for-stmt    = for-iter / for-c
      for-iter    = for-target "in" expr block until-clause?
      for-c       = "for" "(" [ for-init ] ";" [ expr ] ";"
                  [ expr ] ")" block until-clause?
      for-init    = let-stmt / const-stmt / var-stmt / expr-stmt
      for-target  = name / pattern
      until-clause = "until" topic [ "as" name ] block
      match-stmt  = "match" "(" expr ")" "{" 1*( case-arm ) "}"
      case-arm    = "case" pattern [ "if" expr ] block
      pattern     = literal / seq-pattern / name / "_"
      seq-pattern = "[" [ pattern *( "," pattern ) ] "]"
      literal     = number / text / "true" / "false" / "null"
      text        = dq-string / sq-string
      template    = tpl-string
      ctor        = type "(" [ call-arg *( "," call-arg ) ] ")"
      # a type name used as a constructor: Vec<i64>(), i64("42"),
      # Point(x = 1.0); for a primitive it is the Section 10.2
      # conversion function
      # "..." and '...' are one-line strings and never interpolate;
      # `...` is a template string, may span lines, and interpolates
      # ${ident} / ${ident:spec} / ${(expr)} / ${(expr):spec}
      pass-stmt   = "pass"
      let-stmt    = ( "let" / "const" / "var" ) name [ ":" type ]
                  [ "=" expr ]
      fn-def   = [ "async" ] "fn" name "(" [ param *( "," param ) ] ")"
                  [ "->" type ] block
      param       = name [ ":" type ] [ "=" expr ]
                  / "..." name [ ":" type ] / ":::" name [ ":" type ]
      struct-def  = "struct" name "{" 1*( field ) "}"
      field       = name ":" type
      topic       = dq-string / "[" [ dq-string *( "," dq-string ) ] "]"
      # a string may hold OCP wildcards; array elements may mix them
      type        = name [ "<" type *( "," type ) ">" ]
                  *( "[]" / "?" ) / "()"
      name        = ident

      primary     = literal / name / tuple / vec-lit / map-lit / set-lit
                  / on-expr / wait-expr / template / ctor
      tuple       = "(" [ expr *( "," expr ) [ "," ] ] ")" / "(,)"
      vec-lit     = "[" [ expr *( "," expr ) [ "," ] ] "]" / "[,]"
      map-lit     = "{" [ expr ":" expr *( "," expr ":" expr ) ]
                  [ "," ] "}" / "{:}"
      set-lit     = "{" [ expr *( "," expr ) [ "," ] ] "}" / "{,}"
      # {} is always an empty block; empty forms: () (,) [] [,] {:} {,}

      future      = spawn-expr / device-call / sense / actuate
                  / get-param / set-param / ping / status / metadata

      device-call = name "(" [ call-arg *( "," call-arg ) ]
                  [ "@" session ] ")"

   The channel send is lowest precedence in either direction: send-expr
   admits ch <- v and v -> ch; the grammar's unary-expr admits the
   prefix receive <-ch, and the call-arg / select-arm forms admit send
   as well.

Appendix B. Conformance Notes

   A conforming implementation MUST:

   *  accept every construct in Sections 2 to 11 and reject anything it
      does not implement, never silently ignoring it;

   *  treat every device call as a future and every device event as a
      message a program waits for, never blocking the caller before the
      await;

   *  map OCP ERROR codes to the kinds of Table 4 and application
      RESULT errors to their own kind;

   *  honour [RFC0009] and [RFC0010] when the URI scheme selects them,
      and surface an Air peer [RFC0011] without a language change;

   *  cancel cooperatively and fail a cancelled future with Cancel.

   A conforming implementation MAY enforce channel element types, MAY
   add native functions and MAY choose among ready select arms.
